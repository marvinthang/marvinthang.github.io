## Introduction (Lecture 1)

Hosts (computers, phones, servers, ...) connect to the Internet through an **access network**.

### Home / Access Network

Typical path:

Host → Home Router → Modem/ONT → ISP Router

- Hosts connect to a **home router** via Ethernet or Wi-Fi.
- The home router connects to the ISP through a **modem/ONT**.
- DSL/cable commonly use a **modem**.
- Fiber commonly uses an **ONT**.
- The router and modem/ONT may be integrated into one device.

### Internet Core

Typical path:

ISP Router → Router → Router → ... → Destination Network

- **Routers connect to other routers** through network links.
- Routers connect different networks and forward packets between them.
- **Ethernet switches** connect hosts/devices within the same LAN.
- ISPs interconnect through **IXPs, private peering, or transit providers**.

### Physical Media

* **Guided media**: signals travel through a physical medium, e.g. twisted pair, coaxial cable, fiber optics.
* **Unguided media**: signals propagate through free space, e.g. radio/microwave.

### The Network Core

* **Circuit switching**: reserves dedicated resources for a connection/call.
* **Packet switching**: data is divided into discrete chunks called **packets**.
  * **Store-and-forward**: a router receives the entire packet before transmitting it onto the next link.
* Routers **forward packets to the appropriate next hop/output link** based on their forwarding tables.
  * Routing protocols determine the routes/paths used to construct these tables.

### Four Types of Packet Delay

* $d_{proc}$: **processing delay** — check packet/header, determine output link, possibly check bit errors.
* $d_{queue}$: **queuing delay** — time waiting in the output queue before transmission.
* $d_{trans}$: **transmission delay**
  $d_{trans}=\frac{L}{R}$
  where (L) = packet size in bits, (R) = link transmission rate in bits/s.
* $d_{prop}$: **propagation delay**
  $d_{prop}=\frac{d}{s}$
  where (d) = physical link length and (s) = signal propagation speed.

## Application Layer (Lecture 2 + 3)

Client-server architecture and peer-to-peer architecture (P2P).

Transport service need:
* Data integrity: some apps require 100% reliable data transfer, others do not.
* Timing: some apps require low delay, others do not.
* Throughput: some apps require high throughput, others do not.
* Security: encryption, data integrity, authentication

### TCP vs UDP

|                    | TCP                                            | UDP                                                     |
| ------------------ | ---------------------------------------------- | ------------------------------------------------------- |
| Reliability        | Retransmits lost data, preserves order         | Packets may be lost, duplicated, or arrive out of order |
| Flow Control       | Slows sender if receiver cannot keep up        | No built-in flow control                                |
| Congestion Control | Reduces sending rate when network is congested | No built-in congestion control                          |
| Timing             | No latency guarantee                           | No latency guarantee                                    |
| Throughput         | No minimum throughput guarantee                | No throughput guarantee                                 |
| Security           | No built-in encryption/authentication          | No built-in encryption/authentication                   |

### Web

A Web typically consists of:
* base HTML file, and
* several referenced objects (HTML file, images, JavaScript files, CSS files, ...), is addressed by a **URL** (Uniform Resource Locator).

### HTTP: Hypertext transfer protocol

Use TCP as transport service

* Client initiates TCP connection to server
* Server accepts TCP connection request from client
* HTTP messages (requests and responses) are exchanged between client and server
* Client or server closes TCP connection

Two versions of HTTP:

* Non-persistent HTTP (HTTP/1.0): at most one object is sent over a TCP connection. Multiple objects require multiple connections.
  * RTT: Round Trip Time, time for a packet to travel from client to server and go back
  * HTTP Response Time:
    * one RTT to establish TCP connection
    * one RTT for HTTP request and first few bytes of HTTP response to return
    * file transmission time
    * Total = 2 * RTT + file transmission time
* Persistent HTTP (HTTP/1.1): multiple objects can be sent over a single TCP connection between client and server.

Example of HTTP Request:
```http
GET /index.html HTTP/1.1\r\n
Host: www.example.org\r\n
Connection: keep-alive\r\n
...
\r\n
```

Response:
```http
HTTP/1.1 200 OK\r\n
Date: Mon, 23 May 2005 22:38:34 GMT\r\n
Content-Length: 606\r\n
Content-Type: text/html\r\n
...
\r\n
data data data data
```

#### HTTP Request Method types

* HTTP/1.0:
  * GET, POST
  * HEAD: same as GET, but server responds with only HTTP header, no body
* HTTP/1.1:
  * GET, POST, HEAD
  * PUT: upload a file to path specified in the URL
  * DELETE: delete the file specified in the URL

#### HTTP Response Status Codes

* 200 -  OK: request succeeded, requested object is sent in the response
* 301 - Moved Permanently: requested object has moved to a new permanent URL
* 403 - Forbidden: server refuses to respond to request
* 404 - Not Found: requested document is not found on this server

#### Cookies

HTTP is designed to be stateless, but cookies allow servers to maintain state across multiple HTTP requests:

* cookie header field of HTTP request/response message
* cookie file kept on user's host, managed by user's browser
* back-end database at Web site

Client can make a conditional GET request to check if the object has been modified since the last time it was requested. 

The server responds with the object only if it has been modified, otherwise it responds with a `304 Not Modified` status code.

### DNS: Domain Name System

Stores mappings between hostnames and IP addresses (and others) as resource records (RRs) in DNS servers.

RR Format: `(name, value, type, TTL)`

* type=A (Address): `name` is hostname, `value` is IPv4 address
* type=NS (Name Server): `name` is domain name, `value` is name of DNS server responsible for that domain
* type=CNAME (Canonical Name): `name` is alias name, `value` is canonical name
* type=MX (Mail eXchange): `name` is domain name, `value` is name of mail server for that domain

![Desktop View](/assets/img/posts/cs2105/dns.png){: width="972" height="589" }

DNS is hierarchical and distributed. There are usually multiple authoritative DNS servers for each DNS zone for redundancy and availability. These servers serve the same zone data.

For example, resolving `www.google.com`:

- The client queries a recursive DNS resolver for `www.google.com`.
- The resolver queries a root DNS server.
  - The root server is authoritative for the root zone (`.`).
  - It sees the `.com` TLD and returns the authoritative DNS servers for the `.com` zone.
- The resolver queries one of the `.com` TLD DNS servers.
  - These servers are authoritative for the `.com` zone.
  - They return the authoritative DNS servers for `google.com`.
- The resolver queries one of the authoritative DNS servers for `google.com`.
  - These servers store the DNS records for the `google.com` zone.
  - They may be operated by Google itself or by a third-party DNS provider.
- The authoritative server returns the DNS record for `www.google.com` (e.g. an A/AAAA record, or possibly a CNAME).
- The resolver follows any necessary records and returns the resulting IP address to the client.

**Top-level domain (TLD) DNS servers** are authoritative for TLD zones such as `.com`, `.org`, `.net`, `.edu`, and country-code TLDs such as `.sg`, `.uk`, and `.jp`.

#### Local DNS Server

A local DNS server does not strictly belong to the DNS hierarchy. It is usually provided by an ISP, company, or university, and acts as a **recursive DNS resolver**.

DNS cache:
- Resolvers cache DNS records (e.g. A, AAAA, NS, CNAME) together with their **TTL (Time To Live)**.
- A DNS change may take time to be observed by all resolvers on the Internet.

DNS also provides mechanisms for updating authoritative DNS data, e.g. **Dynamic DNS Update**.

- DNS queries normally use **UDP port 53** because most queries/responses are small and retransmission can be handled by retrying the query.
- DNS can use **TCP port 53** when needed, e.g. when a response is too large for UDP or for zone transfers.

There are two types of DNS queries:
- **Iterative query**: the DNS server responds with the best answer it can provide, and may refer the client to another DNS server for further resolution.
- **Recursive query** (rarely used in practice): the DNS server takes on the responsibility of fully resolving the query and returns the final answer to the client.

#### (Optional) DNS Cache Poisoning

DNS cache poisoning is an attack where a DNS resolver is tricked into caching a **fake DNS record**.

Example:
`bank.com → attacker's IP`

Then all clients using that resolver may receive the fake IP until the cached record expires.

- Can redirect users to phishing/malware sites.
- A famous example is the **2008 Kaminsky DNS vulnerability**, which allowed forged DNS replies to poison resolver caches.
- **DNSSEC** helps prevent this by cryptographically authenticating DNS records.

## Transport Layer (Lecture 4 + 5)

Transport layer wraps the **application message/data** with a **TCP or UDP header** containing port numbers, producing a **TCP segment** or **UDP datagram**, then passes it to the network layer.

Network layer wraps the **TCP segment / UDP datagram** with an **IP header** containing source and destination IP addresses, producing an **IP packet/datagram**, then passes it to the link layer.

### UDP: Connectionless Transport

UDP add very little server on top of IP:
* Multiplexing at sender
* Demultiplexing at receiver
* Checksum for error detection

> A UDP server typically uses the same socket to receive datagrams from multiple clients sent to the same local port.  
> A TCP server, in contrast, has one listening socket and creates a new connection socket for each client, while all connection sockets can use the same server port.
{: .prompt-info }

#### UDP Header

Include: 
* Source port number (16 bits)
* Destination port number (16 bits)
* Length (16 bits): length of UDP header + data in bytes
* Checksum (16 bits): optional, used for error detection
* Application data (message)

Advantages of UDP:
* No connection establishment overhead
* Simple: no connection state
* Small header size (8 bytes)
* No congestion control, so can send at full link capacity

#### Checksum

UDP **checksum** is computed as the 1’s complement of the 1’s-complement sum of:
* the IP pseudo-header,
* the UDP header with the checksum field set to 0,
* and the UDP data.

The pseudo-header includes the source IP address, destination IP address, protocol number, and UDP length.

If the computed checksum is 0x0000, it is transmitted as 0xFFFF.

#### UDP Multicast (optional) 

Multicast only supports UDP traffic, so we can't use advantages of TCP, like windowing or ACKs.

> Even though multicast is much more efficient than unicast, it is not widely used for general Internet traffic. One reason is that many ISPs do not support multicast routing, and it can be complex to manage multicast group membership and address allocation.
{: .prompt-info }

There are a designated range of **multicast IP addresses**: 224.0.0.0 to 239.255.255.255. These addresses are only used as destination addresses.

We require applications that support multicast.

Hosts that want to receive multicast traffic must use the **Internet Group Management Protocol (IGMP)** to join a multicast group.  
Routers use IGMP to learn which hosts on their local network want to receive traffic for each multicast group.

When a host wants to join a multicast group, it sends an IGMP **Membership Report** message to the multicast address.  

The router will periodically send IGMP **Membership Query** messages to dest 224.0.0.1 (all hosts multicast address) to check if there are still any hosts interested in that multicast group. When the router receives a Membership Report, its expiry timer will be refreshed.

The host can leave a multicast group by sending an IGMP **Leave Group** message to the multicast address. The router will then send a Membership Query to check if there are any other hosts still interested in that multicast group.

Switches use **IGMP snooping** to learn which ports have hosts that are members of a multicast group, so they can forward multicast traffic only to those ports instead of flooding it to all ports.

There's also a Cisco proprietary protocol called Cisco Group Management Protocol (CGMP) that can be used for multicast group management on Cisco switches.

We use multicast routing protocols to forward multicast traffic between routers and across networks:
* PIM (Protocol Independent Multicast, most popular)
* DVMRP (Distance Vector Multicast Routing Protocol)
* MOSPF (Multicast Open Shortest Path First)

### Principles of Reliable Data Transfer (RDT)

Transport layer resides on end hosts and provides **process-to-process** communication.

Network layer provides **host-to-host, best-effort and unreliable** communication.

Use checksum to detect corrupted packets.  
Use ACKs to confirm successful in-order delivery.  
Use sequence numbers to detect duplicates and identify packet order.  
Use timeout + retransmission to recover from lost packets/ACKs.  
(We don't discuss out-of-order delivery here)

#### Go-Back-N (GBN) Protocol

**Sender:**
- Maintains a sliding window of at most `N` unACKed packets.
- Sends new packets while the window is not full.
- Uses **cumulative ACKs**: `ACK k` means all packets up to `k` were received correctly.
- When an ACK advances the window, sends new packets into the newly available slots.
- Maintains one timer for the **oldest unACKed packet**.
- On timeout, retransmits **all outstanding packets** starting from the oldest unACKed packet.

**Receiver:**
- Keeps track of the **next expected sequence number**.
- If the expected, non-corrupted packet arrives, delivers it to the application and sends an ACK.
- If a packet is corrupted, duplicated, or out of order, discards it and repeats the ACK for the last correctly received in-order packet.
- Does **not buffer out-of-order packets**.

#### Selective Repeat (SR) Protocol

- Receiver **individually ACKs** each correctly received packet.
- Receiver **buffers out-of-order packets** and delivers them to the application once all preceding packets have arrived.
- Sender maintains a **separate timer for each unACKed packet**.
- On timeout, sender retransmits **only that specific packet**, unlike Go-Back-N.

Both sender and receiver maintain **sliding windows**:
- Limits the number of outstanding packets and the amount of buffering/state required.
- Allows pipelining while keeping resource usage bounded.
- With a finite sequence-number space of size `S`, the window size must satisfy  
  `N ≤ S/2` to distinguish new packets from delayed/duplicate packets after sequence numbers wrap around.

### TCP: Connection-oriented Transport

* Point-to-point: one sender, one receiver
* Connection-oriented: handshaking (exchange of control messages) before data transfer
* Full duplex service: bi-directional data flow in the same connection
* Reliable, in-order byte stream: no message boundaries

A TCP connection is uniquely identified by a **4-tuple**: `(source IP, source port, dest IP, dest port)`.

Each connection socket has a **send buffer** and a **receive buffer**.

Send message is broken into **segments** (TCP header + data) and placed in the send buffer.

Max segment size (MSS) is typically 1,460 bytes (Ethernet MTU (Maximum Transmission Unit) of 1,500 bytes minus 40 bytes for IP + TCP headers).

#### TCP Header (20+ bytes)

- ACK number is used only when the `ACK` flag is set.
- Urgent pointer (16 bits) is used when `URG = 1`.

Row 4: Header Info + Flags + Flow Control
- Data offset (4 bits): TCP header size in 32-bit words.
- Reserved (6 bits): normally 0.
- Control flags (6 bits)
  - `URG`: urgent pointer field is valid
  - `ACK`: acknowledgment number field is valid
  - `PSH`: asks receiver to promptly pass received data to the application
  - `RST`: immediately reset/abort the TCP connection
  - `SYN`: synchronize sequence numbers, mainly used during connection establishment
  - `FIN`: sender has finished sending data in this direction
- Window size (16 bits)
  - Number of bytes this endpoint is currently willing to receive.

![Desktop View](/assets/img/posts/cs2105/tcp-header.png){: width="972" height="589" }

#### TCP Reliability: Relation to GBN and SR

TCP is **not exactly Go-Back-N (GBN) or Selective Repeat (SR)**. It combines ideas from both:

- **GBN-like behavior**
  - Uses **cumulative ACKs**: `ACK = y` means all bytes before `y` have been received in order.
  - Typically maintains **one retransmission timer** for the oldest unACKed data.
  - This keeps ACK and timer management relatively simple.

- **SR-like behavior**
  - TCP receivers commonly **buffer out-of-order segments** instead of discarding them.
  - On timeout, TCP retransmits the **oldest unACKed segment**, not all outstanding segments as in GBN.
  - Mechanisms such as Fast Retransmit and SACK allow more selective retransmission, reducing unnecessary transmissions.

This design gets much of GBN's simpler ACK/timer management while avoiding GBN's expensive retransmission of every later segment after a loss.

> TCP does **not require a specific policy for handling out-of-order segments**. An implementation may buffer or discard them, as long as TCP ultimately presents a reliable, in-order byte stream to the application. In practice, modern TCP implementations usually buffer out-of-order data.
{: .prompt-info }

> Guarding against old duplicate packets: A sequence number should not be reused until any old packet with that sequence number is assumed to have disappeared from the network.  
> TCP helps by using a large 32-bit sequence-number space and a bounded packet lifetime; IP TTL prevents packets from circulating forever. For high-speed networks, TCP timestamps/PAWS can also detect old packets after sequence-number wraparound.
{: .prompt-info }

**PAWS (Protection Against Wrapped Sequence numbers)**:
* TCP sequence numbers are only 32 bits, so a long/high-speed connection can eventually wrap around and reuse the same sequence numbers.
* If the **TCP Timestamp** option is enabled, each segment carries a monotonically increasing **TSval**. The receiver maintains a recent timestamp (**TS.Recent**).
* If an incoming segment has a timestamp older than **TS.Recent**, TCP can recognize it as an old duplicate and reject it, even if its sequence number happens to fall inside the current receive window.
* Therefore, PAWS prevents an old segment from being mistaken for new data after sequence-number wraparound.

**TIME-WAIT**: After the FIN exchange completes, the endpoint that performs the final ACK in a normal active close enters TIME-WAIT instead of immediately deleting the connection state.  
It remains there for 2 × MSL (Maximum Segment Lifetime). This serves two main purposes:
* Let old segments from the old connection disappear before the same connection identifiers are safely reused.
* If the final ACK was lost, the peer will retransmit its FIN; the TIME-WAIT endpoint is still around to ACK that FIN again. TCP explicitly says that receiving a retransmitted FIN in TIME-WAIT causes another ACK and restarts the 2-MSL timer.

#### TCP ACK Generation

| Event                                       | ACK Action                                                                                       |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Arrival of in-order segment, no pending ACK | Delayed ACK: wait briefly (up to 500 ms in this model) for the next segment                      |
| Arrival of in-order segment, 1 pending ACK  | Send one cumulative ACK immediately, ACKing both segments                                        |
| Arrival of out-of-order segment             | Immediately send a duplicate ACK for the **next expected byte**                                  |
| Arrival of segment that fills a gap         | Immediately send a cumulative ACK for the **next expected byte after the newly contiguous data** |

#### Timeout Estimation

$\text{EstimatedRTT} = (1 - \alpha) \times \text{EstimatedRTT} + \alpha \times \text{SampleRTT}$

$\text{DevRTT} = (1 - \beta) \times \text{DevRTT} + \beta \times |\text{SampleRTT} - \text{EstimatedRTT}|$

Typically, $\alpha = 0.125$ and $\beta = 0.25$.

$\text{TimeoutInterval} = \text{EstimatedRTT} + 4 \times \text{DevRTT}$

#### Fast Retransmission

Event: if sender receives **3 ACKs** for the same segment, it supposes that segment is lost.  
Action: resend segment **without waiting for the timeout**.

#### Establishing Connection: Three-way handshake (3WHS)

Why TCP needs a 3-way handshake: It is not only for establishing bidirectional communication; it also synchronizes both sides’ initial sequence numbers and confirms that each side has received the other’s fresh ISN, preventing delayed duplicate SYNs from creating stale or half-open connections.

> Server needs to know the client is alive, therefore the client must ACK the server's SYN.
{: .prompt-info }

#### Closing Connection: Four-way handshake (4WHS)

#### TCP Flow Control

- The receiver maintains a **receive buffer** for incoming TCP data.
- The receiver advertises how much more data it is willing to accept using the **receive window (`rwnd`)**, carried in the TCP **Window Size** field.
- `rwnd` is roughly based on the available space in the receiver's receive buffer.
- The sender limits the amount of unACKed/in-flight data according to `rwnd`.
- If `rwnd = 0`, the sender stops sending new data until the receiver advertises more space.

→ Information source: **explicit feedback from the receiver via the TCP Window Size field**.

#### TCP Congestion Control

Causes/costs of congestion:
* throughput can never exceed capacity
* delay increases as capacity approached 
* loss/retransmission + un-needed duplicates decreases effective throughput
* upstream transmission capacity / buffering wasted for packets lost downstream

Approaches to congestion control:
* **End-to-end congestion control**: sender infers congestion from packet loss or delay
* **Network-assisted congestion control**: routers provide explicit feedback to the sender about congestion (e.g. ECN)

#### AIMD (Additive Increase, Multiplicative Decrease)

AIMD (Additive Increase, Multiplicative Decrease) is a common congestion-control algorithm used in TCP: 
* Additive increase: increase `cwnd` by a small amount (e.g. 1 MSS) per RTT when no congestion is detected.
* Multiplicative decrease: 
  * On duplicate ACKs: reduce `cwnd` by a factor (e.g. halve it).
  * On timeout: reduce `cwnd` to 1 MSS (or some fraction of current `cwnd`).

So `min(cwnd, rwnd)` is the effective send window.

Slow Start:
* Start with a small `cwnd` (textbook model: 1 MSS).
* For each ACK of new data, increase `cwnd` by about 1 MSS → `cwnd` roughly doubles every RTT.
* ssthresh determines when to switch to congestion avoidance:
  * When `cwnd` reaches `ssthresh`, switch to additive/linear increase.
  * On timeout, dupACKs: set `ssthresh` ≈ `cwnd`/2, reset `cwnd` = 1 MSS, then enter slow start again.

![Desktop View](/assets/img/posts/cs2105/tcp-congestion-control.png){: width="972" height="589" }

> In **Fast Recovery**, TCP does not immediately return to **Congestion Avoidance**. It stays in **Fast Recovery** until a new ACK acknowledges the retransmitted missing segment.  
> Additional duplicate ACKs indicate that more later segments are still reaching the receiver, so TCP temporarily increases `cwnd` by 1 MSS per extra duplicate ACK, allowing new data to be sent and keeping the pipeline utilized. Once a new ACK arrives, TCP sets `cwnd` = `ssthresh`, exits **Fast Recovery**, and enters **Congestion Avoidance**.
{: .prompt-info }

> Instead of increasing `cwnd` by 1 MSS per RTT in **Congestion Avoidance**, TCP can also increase `cwnd` by `MSS * (MSS / cwnd)` per ACK, which is roughly to 1 MSS per RTT. This allows for smoother growth of `cwnd` and better utilization of the network.
{: .prompt-info }

#### TCP CUBIC

* CUBIC is a TCP congestion-control algorithm designed to probe bandwidth more efficiently than Reno/AIMD, especially on high-bandwidth networks.
* On a congestion/loss event, it records the previous congestion window as `Wmax`, then reduces `cwnd`.
* After the loss, it grows the target congestion window according to a cubic function of **elapsed time since the congestion event**:

$$W(t)=C(t-K)^3+W_{\max}$$

* `Wmax`: `cwnd` around the previous congestion point.
* `t`: elapsed time since the current CUBIC epoch started.
* `K`: time at which the cubic curve reaches `Wmax`, i.e. `W(K)=Wmax`.
* Growth behavior:
  * far below `Wmax` → increase quickly;
  * near `Wmax` → increase slowly/cautiously;
  * beyond `Wmax` with no new congestion → increase faster again to probe for additional bandwidth.
* The cubic curve is flat around `Wmax`, because this is the region where congestion previously occurred.
* Unlike Reno’s roughly `+1 MSS/RTT`, CUBIC’s growth is primarily **time-based**, making it less dependent on RTT; ACKs still drive the actual `cwnd` updates.

#### Delay-based Congestion Control

* Goal: keep the **bottleneck link fully utilized** while avoiding large queues/delay ("keep the pipe just full, but no fuller").
* Maintain `RTT_min`: the minimum observed RTT, approximating RTT when there is little/no queueing.
* Estimate:
  * **Expected uncongested throughput** ≈ `cwnd / RTT_min`
  * **Measured throughput** ≈ `bytes ACKed during an RTT / RTT_measured`
* If measured throughput is close to expected → little congestion → increase `cwnd`.
* If measured throughput is significantly lower → queueing is building up → decrease `cwnd`.
* Unlike loss-based TCP, it detects congestion from **increasing delay before packet loss occurs**.

> Why use throughput instead of RTT directly? Throughput accounts for both the observed delay and the amount of data being sent. The gap between expected and actual throughput, multiplied by roughly one RTT, estimates the amount of data queued in the network, making it a more meaningful congestion signal than raw RTT increase alone.
{: .prompt-info }

#### Explicit Congestion Notification (ECN)

* Two bits in the IP header (ToS field) marked by **network router** to indicate congestion.
* Congestion indication carried to dest.
* Dest sets ECE bit on ACK segment to notify sender of congestion.
* involves both IP (IP header ECN bits) and TCP (ECE and CWR flags) layers.

#### TCP fairness

* **Goal:** If `K` TCP connections share a bottleneck link of capacity `R`, ideally each gets average throughput `R/K`.
* Classic TCP AIMD tends toward fairness: tends to converge toward equal bandwidth sharing.
  * This fairness holds best under ideal assumptions such as similar RTTs and a fixed set of competing TCP flows.
* Fairness is mainly **per TCP connection, not per application**. An application opening multiple parallel TCP connections can obtain multiple shares of the bottleneck bandwidth.
* UDP does not inherently implement TCP-style congestion control, so an uncooperative UDP flow can consume bandwidth without backing off like TCP.

## Network Layer (Lecture 6 + 7)

Network Layer delivers packets to receiving hosts.

A host get an IP address by:
* Static configuration: manually set by system administrator
* Dynamic configuration: automatically assigned by a DHCP (Dynamic Host Configuration Protocol) server

### DHCP: Dynamic Host Configuration Protocol

DORA:
1. Discover: host broadcasts `DHCPDISCOVER` to find available DHCP servers.
2. Offer: DHCP servers respond with `DHCPOFFER`, offering an IP address and configuration.
3. Request: host broadcasts `DHCPREQUEST` to request the offered IP address.
4. DHCP servers respond with `DHCPACK`, confirming the assignment.

DHCP may also provide a host additional network information:
* IP address of first-hop router (default gateway)
* IP address of local DNS server
* Network mask (subnet mask)

DHCP runs over UDP, server uses port 67, client uses port 68.

### The Internet Protocol (IP)

**Network interface**: the attachment point through which a host/router connects to a network (e.g. Wi-Fi, Ethernet, or a virtual interface). An IP address is assigned to an interface, so a device with multiple interfaces can have multiple IP addresses.

An IP address identifies an interface of a host/router on an IP network.
* A host usually has one or two network interfaces (e.g. wired Ethernet and Wi-Fi)
* A router typically has multiple interfaces

**Subnet**: a network formed by a group of "directly" interconnected hosts
* Hosts in the same subnet can communicate directly without a router
* They connect to the outside world through a **default gateway** (router)
* Subnet mask: a bitmask that indicates which bits of IP address are network prefix and which bits are host ID

* **ICANN / Internet registries** allocate large public IP blocks to **ISPs**.
* **ISPs** then divide their block into smaller prefixes and allocate/rent them to **organizations**.
  * Example: ISP owns `200.23.16.0/20`
  * Org 1 gets `200.23.16.0/23`
  * Org 2 gets `200.23.18.0/23`
  * etc.

* Routers forward packets using **Longest Prefix Match**: among all matching routing-table entries, choose the route with the **most specific (longest) prefix**.
  * Example: if both `200.23.16.0/20` and `200.23.18.0/23` match, `/23` wins.
* This is useful when an organization changes ISP but keeps its old prefix: the new ISP can advertise the more specific prefix, and longest-prefix matching routes traffic there.

### Routing Algorithms

* **Intra-AS routing**: routing within an Autonomous System (AS), e.g. OSPF, RIP.
  * Single admin, so no policy decisions are needed
  * Mostly focus on performance
* **Inter-AS routing**: routing between Autonomous Systems, e.g. BGP.
  * Admin often wants to control over how its traffic is routed, who routes through its net, etc.
  * Policy may dominate performance

#### Intra-AS Routing

Abstractly, we can model a network as a **graph**:
* Nodes = routers
* Edges = links between routers
* Link cost: could always be 1, or inverse of bandwidth, or related to congestion, etc.

Link-state routing (LSR) algorithm:
* All routers know the complete network topology and link costs
  * Routers periodically flood link-state advertisements (LSAs) to all other routers in the AS
* Use Dijkstra's algorithm

Distance-vector routing (DVR) algorithm:
* Router know physical-connected neighbors and link costs to them
* Routers exchange distance vectors with neighbors, which contain the best-known distance to each destination and the next hop to reach it
* Use Bellman-Ford algorithm

Routing Information Protocol (RIP) is a simple distance-vector routing protocol:
* Cost metric = hop count (number of routers traversed) (link cost = 1)
* Each router sends its distance vector to all neighbors every 30 seconds through UDP port 520.
* **Self-repair**: if no update from a neighbor for 3 mins, assume neighbor has failed.

#### Network Address Translation (NAT)

NAT routers must:
* Replace `(source IP address, source port)` of outgoing datagrams with `(NAT IP address, new NAT port)` and maintain a mapping table.
* Remember (in NAT translation table) the mapping from `(NAT IP address, new NAT port)` back to `(source IP address, source port)` for incoming datagrams.
* Replace `(NAT IP address, new NAT port)` of incoming datagrams with `(source IP address, source port)` and forward to the correct host.

Benefits:
* No need to rent public IP addresses for all hosts in a private network.
* All hosts use private IP addresses. Can change addresses without affecting the outside world.
* Can change ISPs without changing the private addresses of hosts.
* Hosts inside local network are hidden from the outside world, providing some security.

### Internet Control Message Protocol (ICMP)

Used by hosts and routers to send:
* Error reporting: unreachable host / network / port / protocol
* Echo request/reply (ping)

ICMP messages are carried in IP datagrams, start after IP header and have their own ICMP header: Type + Code + Checksum + others.

Traceroute uses ICMP to discover the path from source to destination. It sends a series of UDP datagrams with increasing TTL values, and each router along the path responds with an ICMP "Time Exceeded" message when the TTL expires. The final destination responds with an ICMP "Port Unreachable" message when it receives a datagram for a closed port.

## Link Layer (Lecture 8 + 9)

Possible Link Layer services:
* Framing: encapsulate datagram into frame, adding header and trailer
* Link access control: when multiple nodes share a link, determine which node can transmit at any given time
* Error detection: detect if bits in the frame have been corrupted
* Error correction: correct bit errors without retransmission
* Reliable delivery: seldom used on low bit-error link (e.g., fiber) but often used
on error-prone links (e.g., wireless link)

Two types of network links:
* Point-to-point link: protocol like PPP, SLIP
* Broadcast link (shared medium): multiple nodes connected to a shared broadcast channel

### Multiple Access Protocols

If two or more nodes transmit simultaneously, a **collision** occurs.

Desired Conversational Characteristics: **etiquettes**

Three broad classes:
* Random access: need to **recover** from collisions
* Taking turns
* Channel partitioning: divide channel into time/frequency/code slots, nodes assigned a slot

Desired properties:
* Collision-free
* Efficient: when only one node want to send data, it can send at rate R
* Fairness: when M nodes want to send data, each can send at average rate R/M
* fully decentralized: no special node to coordinate transmissions

Madantory requirement: coordination about channel sharing must use channel itself, no out-of-band channel.

#### Random Access Protocols

should specify how to detect and recover from collisions

##### Slotted ALOHA - wireless packet switched network

All frames have the same size L, time is divided into slots of size L/R, nodes start to transmit only at the beginning of a time slot (time synchronization).

Retransmit the frame in each subsequent slot with probability p until success.

* Collision-free: No
* Efficiency: 
  * Yes, when only one node has a frame to send, it can send at full rate R
  * No, when multiple nodes have frames to send, average throughput is roughly R/e
* Fairness: Perfectly fair
* Decentralized: Yes

##### Pure (Unslotted) ALOHA

No time slots, no synchronization.

* Efficiency:
  * No, when multiple nodes have frames to send, average throughput is roughly R/(2e)

##### Carrier Sense Multiple Access (CSMA)

Listen before transmitting.

Collisions can still occur due to propagation delay.

##### CSMA/CD (Collision Detection) - used in Ethernet

If a collision is detected, abort the transmission immediately.

Backoff algorithm: binary exponential backoff.

A minimum frame size is required to ensure that the sender is still transmitting when a worst-case collision reaches it: $2\max(d_{prop}) \le d_{trans}$

For example, Ethernet has a minimum frame size of 64 B.

* Collision-free: No
* Efficiency: Yes. When \(d_{prop} \ll d_{trans}\), efficiency approaches 1 because other nodes quickly sense that the channel is busy, so most of the frame transmission time is useful.
* Fairness: Yes
* Decentralized: Yes

#### Channel Partitioning Protocols

##### Time Division Multiple Access (TDMA) - used in GSM

Each node gets fixed length time slots (= data frame transmission time) in each round.

* Collision-free: yes
* Efficient: Inefficient, maximum throughput is R/N
* Fairness: perfectly fair
* Decentralized: yes

##### Frequency Division Multiple Access (FDMA) - used in radio, satellite

Channel spectrum is divided into frequency bands, each node is assigned a fixed frequency band

* Collision-free: yes
* Efficient: Inefficient, maximum throughput is R/N
* Fairness: perfectly fair
* Decentralized: yes

#### Taking-Turns Protocols

##### Polling - used in Bluetooth

One master node polls each of the nodes in a round-robin fashion, each node can transmit up to some maximum number of frames.

* Collision-free: yes
* Efficient: Higher efficiency, but have polling overhead
* Fairness: perfectly fair
* Decentralized: no, master node is single point of failure

##### Token Passing - used in FDDI and token ring

Token is passed from one node to next, sequentially

* Collision-free: yes
* Efficient: Higher efficiency, but have token passing overhead
* Fairness: perfectly fair
* Decentralized: yes

But token loss can be disruptive, node failure can break the ring

### Error Detection and Correction

#### Parity Checks

Use 2-D table with i rows and j columns, so we have i + j + 1 (last one is parity bit for whole table)

Can detect and correct single bit error.

Can detect two-bit error

#### Cyclic Redundancy Check (CRC)

* Uses **polynomial division over modulo 2** (`+` / `-` = XOR).
* If generator $G(x)$ contains factor $(x+1)$, it detects **any odd number of bit errors**.
* For generator degree $r$, detects **every burst error of length $\le r$**.
* For random/equiprobable burst patterns:
  * length $= r+1$: detection probability $1-2^{-(r-1)}$
  * length $> r+1$: detection probability $1-2^{-r}$

### Local Area Networks (LANs)

* Usually same IP subnet, so no router needed to communicate
* Ethernet: wired LAN
  * Media Access Control (MAC) protocol and frame format remain unchanged

#### Ethernet Frame Structure

Sending NIC encapsulates IP datagram in Ethernet frame.

If NIC receives a frame with matching dest address, or with broadcast address, it passes the frame to the network layer.

Data:
* MTU is 1500 bytes, so max Ethernet frame size is 1518 bytes (14 bytes header + 1500 bytes data + 4 bytes CRC)
* Minimum size is 46 bytes

Type: 
* Indicate higher level protocol: IPv4, IPv6, ARP, etc.
* Type field is analogous to:
  * **Protocol field** in IP header
  * **Port number** in TCP/UDP header

Preamble: 7 bytes with pattern 10101010 + 1 byte with pattern 10101011 (SFD, Start Frame Delimiter)
* Used for synchronization between sender and receiver clock rates.

Ethernet is unreliable: no ACK, only retransmitted if initial sender use higher layer rdt (e.g. TCP)

Use **CSMA/CD** to avoid collisions.

##### Bus Topology (popular till mid 90s)

* Use a coaxial bus to interconnect the nodes.
* Is a broadcast LAN.

Drawbacks:
* Back bone cable: if any node / cable fails, the whole network fails.
* Difficult to troubleshoot and maintain.
* Very slow

##### Star Topology (popular now)

Hub:
* **Layer 1 (Physical layer)** device.
* Understands only **individual bits**, not Ethernet frames/MAC addresses.
* When a bit arrives on one port, it **regenerates/repeats** it to **all other ports**.
* All connected devices share one **collision domain** → CSMA/CD needed.

* Cheap + easy maintenance
* But very slow

Switch:
* **Layer-2** LAN device; operates on **Ethernet frames**.
* Learns source MAC → input port automatically.
* Uses destination MAC to selectively forward frames.
* Unknown/broadcast destination → floods to other ports.
* Usually store-and-forward.
* Transparent: hosts are unaware of the switch
* Plug-and-play / self-learning: switch do not need to be configured
* Modern full-duplex switched Ethernet has no collisions / no CSMA/CD.

Switch Forwarding Table:
* Each entry: `<MAC address of host, interface to reach host, TTL>`
* Self-learning: Switch learns source MAC address and interface of incoming frames

When frame received at switch:
* Record incoming link, MAC address of sending host
* Index switch table using deset MAC address
  * If dest on segment from which frame arrived, discard frame
  * Else forward frame 
* Else (entry not found), broadcast to all other links except incoming link

| Router                 | Switch                                      |
| ---------------------- | ------------------------------------------- |
| Layer 3                | Layer 2                                     |
| Check IP address       | Check MAC address                           |
| Store-and-forward      | Store-and-forward                           |
| Compute routes to dest | Forward frame to outgoing link or broadcast |

#### Addressing & ARP

Every NIC has a MAC address:
* When an NIC (adapter) receives a frame, it checks if the dest MAC addr matches its own MAC addr
* Typically 48 bits, burned in NIC ROM (sometime software configurable)
* MAC address allocation is administered by IEEE (first 3 bytes identify the vendor of NIC)

To know MAC address of a host given its IP address, we use **Address Resolution Protocol (ARP)**:
* Each IP node has an **ARP table**:
  * Store mapping of IP address → MAC address of other nodes in same subnet: `<IP address, MAC address, TTL>`
  * If dest MAC addr is not in sender's ARP table, it broadcasts an **ARP request** to all nodes in the subnet (use MAC broadcast address FF:FF:FF:FF:FF:FF)
  * The node with the matching IP address responds with an **ARP reply** containing its MAC
  * The sender caches the mapping in its ARP table for future use
