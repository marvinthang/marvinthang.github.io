## C++

### Barrier

```c++
semaphore mutex = 1;
semaphore turnstile1 = 0;
semaphore turnstile2 = 1;

int count = 0;

void barrier()
{
    // Phase 1: everybody arrives
    mutex.wait();
    count++;

    if (count == N)
    {
        turnstile2.wait();   // close second turnstile
        turnstile1.post();   // open first turnstile
    }

    mutex.post();

    // Pass through turnstile 1
    turnstile1.wait();
    turnstile1.post();


    // Phase 2: everybody leaves
    mutex.wait();
    count--;

    if (count == 0)
    {
        turnstile1.wait();   // close first turnstile
        turnstile2.post();   // open second turnstile
    }

    mutex.post();

    // Pass through turnstile 2
    turnstile2.wait();
    turnstile2.post();
}
```

It must use turnstile for reusable barrier, otherwise one fast thread can pass through the barrier and consume the count of old generation twice.

```c++
std::mutex m;
std::condition_variable cv;

int count = 0;
int generation = 0;

void barrier()
{
    std::unique_lock lock(m);

    int my_generation = generation;

    count++;

    if (count == N)
    {
        count = 0;
        generation++;
        cv.notify_all();
    }
    else
    {
        cv.wait(lock, [&] {
            return generation != my_generation;
        });
    }
}
```

## Valgrind vs AddressSanitizer

|                        | **Valgrind / Memcheck**                     | **AddressSanitizer (ASan)**                |
| ---------------------- | ------------------------------------------- | ------------------------------------------ |
| How enabled            | Run existing binary under `valgrind`        | Compile with `-fsanitize=address`          |
| Instrumentation        | Runtime / dynamic binary instrumentation    | Compiler inserts checks                    |
| Speed                  | Much slower, often **10–30×**               | Usually around **~2×**                     |
| Recompile needed       | Usually no                                  | Yes                                        |
| Invalid reads/writes   | ✅                                           | ✅                                          |
| Use-after-free         | ✅                                           | ✅                                          |
| Heap buffer overflow   | ✅                                           | ✅                                          |
| Stack buffer overflow  | More limited                                | ✅ Very good                                |
| Global buffer overflow | Limited                                     | ✅                                          |
| Memory leaks           | ✅ Excellent                                 | ✅ via LeakSanitizer on supported platforms |
| Uninitialized memory   | ✅ Memcheck detects it                       | ❌ ASan generally doesn't                   |
| Best use               | Deep debugging / leaks / uninitialized data | Everyday development + CI                  |

Valgrind and ASan both detect memory errors, but they work differently. Valgrind uses dynamic binary instrumentation at runtime and tracks memory addressability and definedness, so it can catch invalid accesses, leaks, and uninitialized memory, but it is quite slow. ASan is compiler-based: it inserts checks at compile time and uses shadow memory, red zones, and poisoning to catch things like buffer overflows and use-after-free. ASan is much faster, so I’d usually use it during development and CI, while Valgrind is useful for deeper memory debugging.

### Valgrind

For Valgrind, you can compile your program normally (with the `-g` flag for debugging symbols) and then run it with Valgrind to check for memory leaks and other issues.

Valgrind uses **dynamic binary instrumentation** to run and instrument your program's machine instructions, while storing and checking memory metadata and memory accesses. Valgrind's Memcheck can detect addressability issues, definedness issues (uninitialized memory), memory leaks, use-after-free, and other memory-related errors.

It's quite hard for Valgrind to detect some stack or global buffer overflows, because it does not always know the exact boundary of each object. It mainly knows whether a memory address is valid or not, so if an out-of-bounds access still lands in another valid memory region, it may not detect it.

But it is around 10–30x slower than normal execution, because it is doing a lot of extra work to instrument instructions and track memory usage and errors.

### ASan

ASan is a compiler-based instrumentation tool that adds checks to your code at compile time.

It uses a technique called **shadow memory**, using roughly 1 byte of shadow memory for every 8 bytes of application memory. The shadow memory is used to track whether the corresponding application memory is addressable, partially addressable, or poisoned.

It also uses **red zones** to detect buffer overflows. Red zones are small regions of poisoned memory placed around objects. If a program accesses a red zone, ASan will detect it and report an error.

To handle use-after-free, instead of letting `malloc`/`new` reuse that block immediately, ASan will poison the freed memory and usually put it in a quarantine for a while. This keeps the memory invalid temporarily, so if the program tries to access it through a dangling pointer, ASan can detect it.

It is generally around 2x slower than normal execution, but it is much faster than Valgrind and is practical to use during everyday development and in continuous integration (CI) pipelines. 

### Bonus: TSan

TSan is a compiler-based instrumentation tool used to detect **data races** in multithreaded programs.

For each relevant memory location, TSan stores information about previous reads/writes, such as which thread accessed it and the logical timestamp of that access. When a new read/write happens, it checks whether it conflicts with previous accesses.

Each thread also has a **vector clock**, which stores its knowledge of the logical timestamps of all threads.

Suppose there are two threads A and B:

```text
Vector clock = [A's time, B's time]
Initially:
A: [0, 0]
B: [0, 0]
```

Thread A writes to `x`: `x = 5;`

A updates its clock: `A: [1, 0]`, and TSan remembers: `x` last written by A at time 1

Then A unlocks a mutex: `A: [2, 0]`, `mutex clock = [2, 0]`

Suppose B's clock is: `B: [0, 1]`

When B locks the same mutex, it merges the mutex clock: `B = max([0,1], [2,0]) = [2,1]`

So B now knows that A has completed up to time 2.

Then B reads `x`: `cout << x;`

Since `x` was written by A at time 1: A's write time = 1, and B knows A up to = 2 (1 <= 2), TSan knows the write **happens-before** the read, so there is no race.

Without synchronization:

```c++
// Thread A
x = 5;

// Thread B
cout << x;
```

The clocks may look like:

```text
A: [1, 0]   // writes x
B: [0, 1]   // reads x
```

TSan knows: `x` last written by A at time 1

But B only knows A up to time 0: A's write time = 1, and B knows A up to = 0 (1 > 0)

So there is no happens-before relationship between the accesses.

Because they access the same memory, at least one is a write, and there is no synchronization, TSan reports a **data race**.

> TSan instruments memory accesses and synchronization operations at compile time. At runtime, it keeps shadow metadata for memory locations and logical clocks for threads. It uses happens-before relationships, established by mutexes, atomics, thread creation/join, and other synchronization, to determine whether two conflicting accesses are ordered. If two threads access the same memory, at least one is a write, and there is no happens-before relationship between them, TSan reports a data race.

## Operating Systems

### Malloc

* `malloc(size_t bytes)`: reserve a contiguous block of memory that may be unitinitialized. It will return NULL if the allocation fails.
* `realloc(void *space, size_t bytes)`: resize an existing memory allocation. It may or may not return a new pointer. If realloc fails, it returns NULL and the original pointer is still valid (so you should not overwrite the original pointer until you know realloc succeeded).
* `calloc(size_t nmemb, size_t size)`: take two arguments (number of items and size of each item) and return a pointer to a zero-initialized block of memory. It is equivalent to `malloc(nmemb * size)` followed by `memset(ptr, 0, nmemb * size)`, but it may be more efficient and avoids integer overflow in the multiplication.

#### Heaps and sbrk

The system break (`sbrk`) is used to grow or shrink one contiguous heap segment. It can only grow if the virtual addresses immediately after the current break (the end of the heap) are available.

Because the heap and stack may both grow, they are traditionally placed at opposite ends of the process's address space and grow toward each other.

In older systems, the heap was typically one **contiguous** region grown using `sbrk`.

In modern systems, the heap is better thought of as the collection of dynamically allocated memory managed by the allocator. It may consist of multiple separate virtual-memory regions. The allocator can use `mmap` to request new regions from the OS instead of manually extending one heap with the program break.

The OS mainly tracks which virtual-memory regions are mapped or unmapped, along with their permissions and backing. The C/C++ memory allocator handles heap bookkeeping, such as tracking free and used blocks, splitting and merging blocks, and dealing with fragmentation. When it needs more memory, it can request additional regions from the OS using `mmap`.

`sbrk` knows only about the single traditional program-break heap region. It does not know or care about other regions created with `mmap`.

We can use `sbrk(0)` to get the current program break.

> Fresh memory pages obtained from OS are zero-initialized for security reasons. The OS ensures that a process cannot see leftover data from other processes. But reused memory inside the allocators is not necessary zeroed.

#### Placement Strategy

The result from [Wilson et al. 1995](https://www.cs.jhu.edu/~huang/cs318/fall21/readings/wilson.pdf)

- **Best-Fit:** May leave tiny, unusable free blocks (external fragmentation). A minimum splitting threshold avoids this by allocating the whole block if the leftover is too small, at the cost of internal fragmentation. However, tiny fragments and worst-case behavior are less common in typical workloads.
- **First-Fit:** Address-ordered and LRU generally perform better than MRU.
- **In practice:** Best-Fit and First-Fit have similar memory utilization when using splitting thresholds and coalescing.

**Notes:**
- **Best-Fit:** Can stop searching early when an exact fit or an acceptable near-fit (within a threshold) is found. Can use a BST or segregated free lists for faster searches.
- **Worst-Fit:** Can use a max-heap to find the largest free block efficiently.
- **First-Fit:** Requires an ordering of free blocks:
  - **LRU/MRU:** Can use a doubly linked list for $O(1)$ insertion.
  - **Address-ordered:** Can use a skip list to reduce insertion from $O(n)$ to expected $O(\log n)$. First-Fit search remains $O(n)$, unless augmented with range maximum block sizes.
```c++

#include <bits/stdc++.h>
using namespace std;

class FirstFitSkipList {
    static constexpr int H = 20;

    struct Node {
        uintptr_t addr;
        size_t bytes;
        vector<Node*> next;
        vector<size_t> mx;

        Node(uintptr_t a, size_t b, int h)
            : addr(a), bytes(b),
              next(h, nullptr), mx(h, 0) {}
    };

    Node* head = new Node(0, 0, H);
    mt19937 rng{1234567};

    int randomHeight() {
        int h = 1;
        while (h < H && (rng() & 1))
            ++h;
        return h;
    }

    // Maximum block size in (from, to].
    // Uses the summaries at the level below.
    static size_t rangeMax(Node* from, Node* to, int level) {
        size_t ans = 0;

        while (from != to) {
            ans = max(ans, from->mx[level]);
            from = from->next[level];
        }

        return ans;
    }

    // Find predecessor at every level, ordered by address.
    array<Node*, H> predecessors(uintptr_t addr) const {
        array<Node*, H> prev{};
        Node* p = head;

        for (int l = H - 1; l >= 0; --l) {
            while (p->next[l] && p->next[l]->addr < addr)
                p = p->next[l];

            prev[l] = p;
        }

        return prev;
    }

public:
    ~FirstFitSkipList() {
        Node* p = head;
        while (p) {
            Node* nxt = p->next[0];
            delete p;
            p = nxt;
        }
    }

    FirstFitSkipList(const FirstFitSkipList&) = delete;
    FirstFitSkipList& operator=(const FirstFitSkipList&) = delete;
    FirstFitSkipList() = default;

    bool insert(uintptr_t addr, size_t bytes) {
        assert(bytes > 0);

        auto prev = predecessors(addr);

        if (prev[0]->next[0] &&
            prev[0]->next[0]->addr == addr)
            return false;

        Node* node = new Node(addr, bytes, randomHeight());

        // Bottom-up: lower-level maxima are fixed first.
        for (int l = 0; l < H; ++l) {
            Node* p = prev[l];
            Node* old = p->next[l];

            if (l < (int)node->next.size()) {
                node->next[l] = old;
                p->next[l] = node;

                if (l == 0) {
                    p->mx[0] = bytes;
                    node->mx[0] = old ? old->bytes : 0;
                } else {
                    p->mx[l] = rangeMax(p, node, l - 1);
                    node->mx[l] = old
                        ? rangeMax(node, old, l - 1)
                        : 0;
                }
            } else if (old) {
                // Existing interval now contains the new node.
                p->mx[l] = max(p->mx[l], bytes);
            }
        }

        return true;
    }

    bool erase(uintptr_t addr) {
        auto prev = predecessors(addr);
        Node* victim = prev[0]->next[0];

        if (!victim || victim->addr != addr)
            return false;

        // Repair summaries from bottom to top.
        for (int l = 0; l < H; ++l) {
            Node* p = prev[l];

            // Unlink if victim appears at this level.
            if (p->next[l] == victim)
                p->next[l] = victim->next[l];

            Node* end = p->next[l];

            // Recompute the affected interval maximum.
            if (l == 0) {
                p->mx[0] = end ? end->bytes : 0;
            } else {
                p->mx[l] = end
                    ? rangeMax(p, end, l - 1)
                    : 0;
            }
        }

        delete victim;
        return true;
    }

    optional<pair<uintptr_t, size_t>>
    firstFit(size_t request) const {
        if (request == 0)
            return nullopt;

        Node* p = head;

        for (int l = H - 1; l >= 0; --l) {
            // Skip intervals where no block can fit.
            while (p->next[l] && p->mx[l] < request)
                p = p->next[l];
        }

        Node* ans = p->next[0];

        if (!ans || ans->bytes < request)
            return nullopt;

        return pair{ans->addr, ans->bytes};
    }
};
```

#### Malloc Implementation

Each memory block stores **metadata (header)** at the beginning, including its size and allocation status. A **boundary tag (footer)** can store the size again, allowing the next block to locate the previous block for coalescing.

- **Implicit navigation:** No need to store a pointer to the next physical block, since its address can be computed using the current block's address and size (lower overhead).
- **Alignment:** Round up allocation sizes when needed to satisfy alignment requirements.

Modern allocators (e.g., **glibc malloc**) combine implicit navigation with:
- **Explicit free lists:** Traverse only free blocks, with next/prev pointers stored inside free blocks.
- **Segregated free lists:** Group free blocks by size to speed up allocation.

#### SLUB Allocator (Linux Kernel)

SLUB is a **slab allocator** that uses size classes to provide fast allocation with low memory overhead.

- **Size classes:** Round each request up to the smallest supported size (e.g., 80 bytes → 96 bytes).
- **Slabs:** Each size class manages slabs consisting of one or more memory pages (typically 4 KiB per page). Each slab is divided into fixed-size slots.
- **Free lists:** Track available slots within each slab. Allocation takes a free slot; freeing returns it to the free list.
- **Minimal splitting/coalescing:** Individual slots have fixed sizes, so they don't need splitting or coalescing. Empty slabs can release their pages.
- **Tradeoff:** Some internal fragmentation in exchange for fast allocation, low metadata overhead, and good cache locality.

#### Comparison

| Policy    | Advantages                           | Disadvantages                                  | Time Complexity                   |
| --------- | ------------------------------------ | ---------------------------------------------- | --------------------------------- |
| First-Fit | Simple, can stop early               | Depends on free-list order                     | O(n) scan                         |
| Best-Fit  | Preserves larger blocks              | May create tiny unusable fragments             | O(n) scan; O(log n) with BST      |
| Worst-Fit | Leaves larger remainders             | Breaks up large blocks; often poor utilization | O(n) scan; O(log n) with max-heap |
| Next-Fit  | Avoids repeatedly scanning from head | May worsen fragmentation                       | O(n) worst case                   |

| Data Structure         | Advantages                    | Disadvantages                                  |
| ---------------------- | ----------------------------- | ---------------------------------------------- |
| Implicit list          | Simple, low metadata overhead | Scans allocated and free blocks                |
| Explicit free list     | Only scans free blocks        | Extra pointers and updates                     |
| Segregated free lists  | Fast search by size class     | More bookkeeping                               |
| Balanced BST (by size) | O(log n) Best-Fit search      | Tree metadata and rebalancing                  |
| Max-heap               | O(log n) Worst-Fit allocation | Arbitrary removal is harder                    |
| Skip list (by address) | Expected O(log n) insertion   | First-Fit search remains O(n) unless augmented |

| Allocator                  | How It Works                                      | Advantages           | Disadvantages                                 |
| -------------------------- | ------------------------------------------------- | -------------------- | --------------------------------------------- |
| General-purpose free-block | Variable-sized blocks with splitting/coalescing   | Flexible, good reuse | Fragmentation and metadata overhead           |
| Buddy                      | Power-of-two blocks, recursively split/merge      | Easy coalescing      | Internal fragmentation                        |
| Slab / SLUB                | Pages divided into fixed-size slots by size class | Fast, good locality  | Internal fragmentation; partially empty slabs |
| Arena / Bump               | Sequential allocation from a region               | Very fast, O(1)      | Usually no individual free                    |

#### Page Table

A **page** is a fixed-size block of virtual memory, while a **frame** is a block of physical memory of the same size. The OS maintains page tables mapping virtual pages to physical frames.

TLBs often have high associativity (small ones may be fully associative) to reduce expensive misses. Fully associative TLBs compare tags in parallel.

**Page Faults:**

- **Minor:** Valid memory access that can be resolved without disk I/O.
  - Example: `mmap()` initially creates a virtual memory area (VMA), but may not allocate physical frames or populate PTEs.
  - **First read:** For anonymous `mmap()`, Linux may map the page to a shared, read-only zero page, since anonymous memory must initially contain zeros.
  - **First write:** Kernel allocates a zero-filled physical frame and updates the PTE to point to it with write permission.
  - Can also occur with copy-on-write (COW) or file pages already in the page cache.
- **Major:** Valid access requiring data to be loaded from disk (swap or file).
  - Kernel loads the page into RAM and updates the PTE. It may need to evict another page if memory is insufficient.
  - Frequent paging can cause **thrashing**: the system spends most of its time swapping pages instead of executing useful work.
- **Invalid:** Access to an unmapped address or violation of memory permissions.
  - Kernel checks the VMA and usually sends `SIGSEGV` if the access is invalid.

#### mmap

Mapping to a frame backed by a disk file, or shared among processes.

The OS only allocates corresponding physical frames when the process actually accesses the mapped memory. It also only writes back to the file when the page is dirty and needs to be evicted.

`prot`: what operations are allowed on the mapped memory (read, write, execute).
* `PROT_READ`: allow reading, require fd to be readable
* `PROT_WRITE`: allow writing, require fd to be writable or a private mapping
* `PROT_EXEC`: allow execution, require fd to be executable
* `PROT_NONE`: no access allowed, useful for security (surround critical data with guard pages)

`flags`: how the mapping behaves
* `MAP_SHARED`: changes are visible to other processes mapping the same file, and are written back to the file
* `MAP_PRIVATE`: changes are private to the process, and are not written back to the file (copy-on-write)

Can also use `msync()` to explicitly flush dirty pages to disk (synchronize change to file, but not evict the page)

`mmap` requires the offset to be aligned to the system page size. So you have to modify your offset to the nearest page boundary.
```c
off_t offset = 5000;
size_t length = 1000;

struct stat sb;
int fd = open(argv[1], O_RDONLY);
fstat(fd, &sb);

off_t page_offset = offset & ~(sysconf(_SC_PAGE_SIZE) - 1);

char * addr = mmap(NULL, length + offset - page_offset, PROT_READ, 
                    MAP_PRIVATE, fd, page_offset);

write(1, addr + offset - page_offset, length);

munmap(addr, length + offset - page_offset);
close(fd);
```

```c
int size = 100 * sizeof(int);
void *addr = mmap(0, size, PROT_READ | PROT_WRITE, MAP_SHARED | MAP_ANONYMOUS, -1, 0);
int *shared = addr;

pid_t child = fork(); // fork child process for shared memory communication
```

This is an efficient form of IPC because there is no copying data between processes, system call for each memory access (like pipe), or disk-access overhead, but we need explicit synchronization to avoid data races.

#### Pipes

A pipe has a limited buffering capacity (typically 64 KiB on Linux). If a process writes more data than the pipe can hold, the write will block until some data is read from the pipe. Similarly, if a process tries to read from an empty pipe, it will block until data is written to the pipe.

If a writer writes to a pipe but no process has its read end open, the kernel sends `SIGPIPE` to the writer, which by default terminates the process. If the writer ignores or handles `SIGPIPE`, the write will fail with `EPIPE`.

The reason for `SIGPIPE` is to provide automatic termination when a pipeline's consumer exits. For example, this terminates cat when their remaining output is no longer needed:

```bash
cat largefile | head -n 10
```

> Pipe writes of at most `PIPE_BUF` bytes are atomic (not interleaved with other writers). If there isn't enough space, a blocking write waits, while a nonblocking write fails with `EAGAIN`. Writes larger than `PIPE_BUF` may be interleaved or partially completed, depending on the blocking mode.
{: .prompt-info }

```c
pipe2(filefd, O_CLOEXEC)

execve("/bin/ls", argv, envp)
// no need for close(filefd[0]) or close(filefd[1]) because O_CLOEXEC will automatically close the file descriptors on exec()
```

`fdopen(fd, mode)` wraps an existing file descriptor in a `FILE*`, allowing standard C I/O functions (`fprintf`, `fgets`, etc.) and buffering.
- `fopen()` opens a file and creates a `FILE*`.
- `fdopen()` creates a `FILE*` from an existing descriptor, without duplicating it.
- `fclose()` flushes buffered output and closes the underlying descriptor.
- `fflush()` is important for pipes because `fprintf()` may buffer output instead of writing immediately.
  
Useful for pipes and sockets, where we already have a file descriptor but want convenient formatted or buffered I/O.

**Named pipes (FIFOs)** are similar to unnamed pipes but have a pathname in the filesystem. The pathname identifies a kernel-managed pipe; data is buffered in the kernel, not stored in the filesystem. FIFOs allow unrelated processes to communicate without inheriting file descriptors.

- `mkfifo(path, mode)`: Creates the FIFO but does not open it.
- `open(path, O_RDONLY/O_WRONLY)`: Opens the FIFO and returns a file descriptor.
- `open()` may block until another process opens the other end.
- `read()` / `write()`: Transfer data through the kernel pipe buffer.
- `close()`: Closes the descriptor; `unlink()` removes the FIFO pathname.

```c
//Program 1
int main(){
    int fd = open("fifo", O_RDWR | O_TRUNC);
    write(fd, "Hello!", 6);
    close(fd);
    return 0;
}
  
//Program 2
int main() {
    char buffer[7];
    int fd = open("fifo", O_RDONLY);
    read(fd, buffer, 6);
    buffer[6] = '\0';
    printf("%s\n", buffer);
    return 0;
}
```
Program 1 open the FIFO with `O_RDWR` to avoid blocking, but when it will act as both reader and writer, so the `write()` is not blocked, but when it `close(fd)`, the FIFO is closed and kernel will discard the buffer, so Program 2 will read nothing and block forever.

**File Descriptors and `fork()`**

The **kernel file offset** is the current read/write position, stored in the **open file description**. It is automatically updated by `read()` / `write()` and can be changed using `lseek()`.

After `fork()`:
- Parent and child have separate file descriptor tables, but inherited descriptors refer to the **same open file description**, so they share the kernel file offset.
- `read()`, `write()`, and `lseek()` in one process can affect the file position seen by the other.
- `close()` in one process does not close the descriptor in the other.
- Separate `open()` calls create different open file descriptions with independent offsets.

**`FILE*` Buffering and `fork()`**

`FILE*` provides user-space buffering on top of file descriptors.

- `fgetc()` may internally read more bytes than requested, advancing the kernel file offset while keeping unread bytes in its user-space buffer.
- After `fork()`, parent and child have **separate copies of the `FILE*` buffer**, but still share the underlying kernel file offset.
- This can cause inconsistencies because the buffers and shared offset may become out of sync.
- `fclose()` may reposition the shared kernel offset to account for unread buffered data.

### how to design OS mechanism to handle segfault to call stack trace to clean object then exit like Python or Java

You generally should not throw a C++ exception directly from a SIGSEGV handler, because signal handlers run in an asynchronous context and normal C++ exception handling is not guaranteed to be safe there.
A low-level way to bridge SIGSEGV into a C++ exception is to install the handler with sigaction(..., SA_SIGINFO). The handler receives the saved thread context, including the program counter. If the fault is one that we intentionally support, the handler changes the saved program counter so that, after the handler returns, execution resumes in a small recovery/trampoline function instead of at the faulting instruction.
That trampoline is now executing in normal user code, outside the signal handler, so it can throw a regular C++ exception. Then normal stack unwinding happens and RAII destructors run.
This is only reasonable for known, controlled fault locations. For an arbitrary segmentation fault, the process may already have corrupted state, so trying to unwind and continue is unsafe; normally you log minimal crash information and terminate.

We rewrite the saved instruction pointer to a trampoline and ensure the stack/register context satisfies the normal ABI. The trampoline then throws normally, so the C++ unwinder sees valid stack frames and can run destructors.


### User Mode vs Kernel Mode

User mode and kernel mode are **hardware-supported** CPU privilege modes. During boot, the OS configures the hardware mechanisms that determine where execution should enter the kernel when a system call, exception, or interrupt occurs. 
* For example, on x86, interrupts/exceptions use the IDT, while `SYSCALL` uses separately configured syscall-entry registers.

The OS normally runs application code in user mode and kernel code in kernel mode, while the CPU hardware enforces the privilege restrictions.

When a system call, exception, or interrupt transfers execution into the kernel, the hardware performs the privilege transition and saves enough machine state to allow execution to return later. Kernel entry code then saves any additional register state it needs and runs the appropriate handler.

> x86 detail: For an interrupt or exception that changes privilege from user mode to kernel mode, the CPU switches to a kernel stack and pushes a hardware-defined frame containing state such as the old `RIP`, `CS`, `RFLAGS`, and, on a privilege change, the old RSP/SS. **Kernel entry assembly** (from OS) then typically saves the remaining GPRs.  
> However, x86-64 SYSCALL behaves differently: it saves the user return address and flags in registers (RCX and R11) and does not automatically construct the same interrupt-style stack frame; the kernel entry code handles the stack switch and additional saving.

### Basic Relationships

#### Synchronizes-with relationship

Only on atomic types. A suitably-tagged atomic write on a variable (x) **synchronizes-with** a suitably-tagged atomic read on the same variable (x) that reads the release write's value directly or a value produced through a chain of atomic operations starting from that write.

That means everything that happens before the write is visible to everything that happens after the read.

#### Happens-before relationship

There are **happens-before** and **strongly-happens-before** relationships.

For single thread, if A is sequenced-before B, then A **happens-before** B.

**Synchronizes-with** relationships are a subset of **happens-before** relationships. If A **synchronizes-with** B, then A **happens-before** B.

Combining with sequenced-before relationships: if A is sequenced-before B, and B **inter-thread happens-before** C, then A **happens-before** C.

**Strongly-happens-before** is slightly different, but in most cases comes down the same:
* If A synchronizes-with B, or A is sequenced-before B, then A **strongly-happens-before** B.
* Transitivity: if A **strongly-happens-before** B, and B **strongly-happens-before** C, then A **strongly-happens-before** C.
* The difference is `memory_order_consume`, which contributes to **happens-before** but not **strongly-happens-before**. It is a weaker ordering than `memory_order_acquire`, and it is not widely used in practice. We use **happens-before** in the rest of the notes, and it is usually equivalent to **strongly-happens-before**.

### Memory Ordering

There are six memory orderings in C++:
* `memory_order_relaxed`: no ordering guarantees, only atomicity
* `memory_order_consume`: a weaker form of acquire, only enforces ordering on dependent reads (not widely used)
* `memory_order_acquire`: prevents memory reordering of subsequent reads and writes after the acquire operation
* `memory_order_release`: prevents memory reordering of previous reads and writes before the release operation
* `memory_order_acq_rel`: combination of acquire and release
* `memory_order_seq_cst`: sequentially consistent, the strongest ordering, all threads see operations in the same order

On some architectures like ARM, the hardware allows lots of reordering, so we need extra ordering work to enforce the memory orderings. On x86, the hardware already enforces a lot of ordering, so some memory orderings are effectively no-ops.

#### Sequentially Consistent (SC) Ordering

All threads must see the same order of operations. That means there exists a total order of all memory operations that is consistent with the program order of each thread.

This is quite expensive to enforce in weakly-ordered machine, but for strongly-ordered machine like x86 or x86-64, it is quite cheap.

#### Relaxed Ordering

The only requirement is that access to a single atomic variable from the same thread cannot be reordered.

The cache coherence protocol already ensures that all threads see the same order of operations on a single atomic variable, so we don't need to do anything extra for that.

There is no **synchronizes-with** relationship between threads even **happens-before** relationship is established within a single thread.

> The difference between normal `int x` and `std::atomic<int> x` with relaxed ordering is that the compiler may assume an ordinary int is not being concurrently modified without synchronization; otherwise the program has a data race and UB. Therefore it may cache, eliminate, or reorder ordinary accesses. For an atomic variable, the compiler must preserve the semantics of the atomic loads/stores and cannot simply assume another thread won’t change it. Relaxed atomics still provide atomicity and per-object coherence, but no cross-variable synchronization or ordering.
{: .prompt-warning }

Think of **each atomic variable as one person with a notebook**.

- The notebook contains that variable’s **modification order**
- Each thread has its own **bookmark** in that notebook.
- A normal relaxed `load()` may return the current bookmarked value or move **forward** to a newer value, but never backward.
- A relaxed `store(v)` appends `v` to the end of the notebook.
- Different atomic variables have completely separate notebooks → **no ordering relationship between them**.
- Different threads may have bookmarks at different positions, so they can observe the same atomic at different stages.

**RMW operations are special:**

```c++
exchange()
fetch_add()
compare_exchange()
```

They must operate on the **latest/bottom value** of the modification order at the point where the RMW occurs, so they read the latest value and then write a new value based on that. This is important for implementing locks, semaphores, and other synchronization primitives.

#### Acquire-Release Ordering

A release operation **synchronizes-with** an acquire operation on the same atomic variable.

If you mix acquire-release operations with SC operations, the SC operations loads behave like acquire, SC stores behave like release, and SC RMW operations behave like acquire-release.

Relaxed operations are still relaxed, but are bound by the additional synchronizes-with relationships established by acquire-release operations.

Locking a mutex is an acquire operation, and unlocking a mutex is a release operation. Therefore, all operations before the unlock are visible to all operations after the lock.

`memory_order_consume` is a weaker form of acquire, which only enforces only operations that depend on the loaded value. It uses **dependency-ordered-before** instead of **synchronizes-with**. Difficult to implement and rarely useful. Deprecated in C++26 (effectively becomes `memory_order_acquire`).

```c++
X* x = p.load(std::memory_order_consume);

x->i;   // depends on x
x->s;   // depends on x

a.load(std::memory_order_relaxed); // unrelated to x
```

**Release sequence**: a release store followed by a chain of atomic RMW operations on the same atomic object. The RMWs may even be relaxed. If an acquire load reads a value produced by that sequence, it synchronizes with the original release store.

```c++
std::atomic<int> x{0};
int data = 0;

// Thread A
data = 42;
x.store(1, std::memory_order_release);   // A

// Thread B
x.fetch_add(1, std::memory_order_relaxed); // B: reads 1, writes 2

// Thread C
x.fetch_add(1, std::memory_order_relaxed); // C: reads 2, writes 3

// Thread D
int v = x.load(std::memory_order_acquire); // D: reads 3
```

Release sequence is essentially used for multiple acquire operations from multiple threads to synchronize with a single release operation (but there is no synchronizes-with relationship between the acquire operations themselves).

```c++
// Producer:
queue_data initialized
count.store(20, release)        // A

// Consumer 1:
int idx = count.fetch_sub(1, acquire)     // B: reads 20, writes 19
consume queue_data[idx]

// Consumer 2:
int idx = count.fetch_sub(1, acquire)     // C: reads 19, writes 18
consume queue_data[idx]
```

### Fences

```c++
// A
void write_x_then_y() {
    x.store(true,std::memory_order_relaxed);
    std::atomic_thread_fence(std::memory_order_release);
    y.store(true,std::memory_order_relaxed);
}

// B
void read_y_then_x() {
    while(!y.load(std::memory_order_relaxed));
    std::atomic_thread_fence(std::memory_order_acquire);
    if(x.load(std::memory_order_relaxed))
        ++z;
}
```

We have:
```text
A: RELAXED STORE x
 ↓ sequenced-before
A: RELEASE FENCE
 ↓ sequenced-before
A: RELAXED STORE y
 ↓ reads-from
B: RELAXED LOAD y   // sees true from A's store
 ↓ sequenced-before
B: ACQUIRE FENCE
 ↓ sequenced-before
B: RELAXED LOAD x
```

The combination of sequenced-before and relaxed reads-from relationships establishes a **happens-before** relationship between the release fence in A and the acquire fence in B.

If an atomic read before an **acquire fence** reads a value written by a **release operation** (or its release sequence), that release operation synchronizes-with the acquire fence.

Any release operation can synchronize-with an acquire fence through reads-from or release sequence.

> In C++, there is no synchronizes-with relationship between atomic operations of different atomic variables, even if they are both release/acquire operations. But it may work on x86 machine because x86 memory model is stronger than C++ requires.
{: .prompt-info }

##### `std::thread`
For `std::thread`, thread creation and `join()` provide implicit synchronization:
- Operations before the thread is started **happen-before** operations in the new thread.
- Operations performed by the worker thread **happen-before** operations after `join()` returns.

This is release/acquire-like synchronization, but not literally an explicit fence.

##### `std::promise` / `std::future`

`promise.set_value()` or `set_exception()` **synchronizes-with** a successful `future.get()`, `wait()`, or a wait operation that returns `ready`.

Everything before `set_value()` happens-before code after the future becomes ready.

If the `promise` is destroyed without setting a value, it stores a `future_error` (`broken_promise`); observing that ready future also synchronizes.

##### `std::packaged_task`

Completion of the packaged task synchronizes-with the associated future becoming ready / returning from `get()` or `wait()`.

If the packaged task is destroyed before running, the future receives an exception similarly.

##### `std::async`

Completion of the async task synchronizes-with successful `future.get()/wait()`.

For `launch::deferred`, the task may actually run inside the thread that calls `get()`/`wait()`, but the same completion-before-return guarantee applies.

### Shared Pointer Implementation

```c++
// weak ptr lock
long count = strong_count.load();

while (count != 0) {
    if (strong_count.compare_exchange_weak(
            count, count + 1)) {
        // success: object guaranteed alive
        return shared_ptr(...);
    }
}

return {}; // object already dead
```

CAS weak allows spurious failure (allowed to fail even if the value is equal), so we need to retry until we succeed. C++ allow this because some CPUs does not have a strong CAS instruction, and they use Load-Linked/Store-Conditional (LL/SC) instead:
* LL: value = x, remember that it is watching x
* SC: if its watch is still valid, store new value to x and return true, otherwise return false
* The watch can be lost even if x still have the same value, this causes spurious failure, so we need to retry until we succeed.

CAS weak is usually faster than CAS strong, so it is prefered for **retry loops**.

There is one **fake/implicit weak reference whenever `strong_count > 0`**. Without the implicit weak reference, we might try to implement destruction like this:

```c++
~shared_ptr() {
    if (strong_count.fetch_sub(1, release) == 1) {
        atomic_thread_fence(acquire);
        delete ptr;

        if (weak_count.load(relaxed) == 0) {
            atomic_thread_fence(acquire);
            delete control_block;
        }
    }
}

~weak_ptr() {
    if (weak_count.fetch_sub(1, release) == 1 &&
        strong_count.load(relaxed) == 0) {
        atomic_thread_fence(acquire);
        delete control_block;
    }
}
```

Suppose there is one `shared_ptr` and one `weak_ptr`, and both are destroyed concurrently. Even though `strong_count` and `weak_count` are individually atomic, the combined operation is **not atomic**. Therefore both threads can observe that the other counter is `0` and both decide to: `delete control_block`.

There is also no synchronization between two atomic variables, so both can observe the other counter as `1` and none of them delete the control block, leading to a memory leak.

```c++
~shared_ptr() {
    if (strong_count.fetch_sub(1, release) == 1) {
        atomic_thread_fence(acquire);

        delete ptr;

        // Drop the implicit weak reference
        if (weak_count.fetch_sub(1, release) == 1) {
            atomic_thread_fence(acquire);
            delete control_block;
        }
    }
}

~weak_ptr() {
    if (weak_count.fetch_sub(1, release) == 1) {
        atomic_thread_fence(acquire);
        delete control_block;
    }
}
```

Now deletion of the control block is owned by exactly one atomic transition:

```text
weak_count: 1 → 0
```

Only the thread that performs this transition deletes the control block.

Example with one `shared_ptr` and one real `weak_ptr`:

```text
strong = 1
weak   = 2
         = 1 real weak + 1 implicit weak
```

If the `shared_ptr` dies first:

```text
strong: 1 → 0
delete object
weak:   2 → 1     // remove implicit weak

weak_ptr later:
weak:   1 → 0
delete control block
```

If the `weak_ptr` dies first:

```text
weak: 2 → 1

shared_ptr later:
strong: 1 → 0
delete object
weak:   1 → 0     // remove implicit weak
delete control block
```

So the implicit weak reference converts a dangerous two-counter check into a single atomic `weak_count: 1 → 0` decision.

### GIL

GIL allows only one thread to run Python bytecode at a time, effectively making Python single-threaded. However, Python can still use multiple threads for I/O-bound tasks, as the GIL is released during I/O operations (Concurrency).


Can CPython have true parallelism?  
Yes. In normal GIL-enabled CPython, only one thread can execute Python bytecode at a time. However, native C/C++ code can explicitly release the GIL while performing work that does not require access to Python interpreter state / Python objects. During that section, multiple threads can execute native code simultaneously on different CPU cores, giving true parallelism. Blocking I/O also commonly releases the GIL.

### Traps

Default argument:

```py
def f(x=[]):
    x.append(1)
    return x

f()  # returns [1]
f()  # returns [1, 1] because the default list is shared across calls
```

Every call to `f()` without an argument uses the same default list, leading to multiple appends to the same list. To avoid this, use `None` as the default value and create a new list inside the function:

```py
def f(x=None):
    if x is None:
        x = []
    x.append(1)
    return x
```

Late-binding closure:

```py
def make_funcs():
    funcs = []
    for i in range(3):
        def f():
            return i
        funcs.append(f)
    return funcs
```

The functions returned by `make_funcs()` will all return `2`, because they capture the variable `i` by reference (not the object `i` points to at the time of function creation). This is 

A local variable becomes a cell variable (a variable that is shared between a function and its nested functions) when a nested function/lambda references it. In the example above, `i` is a cell variable because the inner function `f()` references it.

To fix this, you can use a default argument to capture the current value of `i` at each iteration:

```py
def make_funcs():
    funcs = []
    for i in range(3):
        def f(i=i):  # capture current value of i
            return i
        funcs.append(f)
    return funcs
```

Code decorator for python function that support async function

```py
import asyncio

def async_cache(func):
    cache = {}
    in_flight = {}

    async def wrapper(*args, **kwargs):
        key = (args, tuple(sorted(kwargs.items())))

        if key in cache:
            return cache[key]

        if key not in in_flight:
            in_flight[key] = asyncio.create_task(
                func(*args, **kwargs)
            )

        task = in_flight[key]

        try:
            result = await task
        except Exception:
            if in_flight.get(key) is task:
                del in_flight[key]
            raise

        cache[key] = result

        if in_flight.get(key) is task:
            del in_flight[key]

        return result

    return wrapper
```

## Hashing

### Separate Chaining vs Open Addressing

|                    | Separate Chaining                                          | Open Addressing                                           |
| ------------------ | ---------------------------------------------------------- | --------------------------------------------------------- |
| Load factor        | Can exceed 1                                               | Must be <= 1                                              |
| When table is full | Performance degrades gracefully                            | Performance degrades sharply                              |
| Memory locality    | Poor: forward list buckets                                 | Better: flat array                                        |
| Cache performance  | Poor: pointer chasing                                      | Better: flat array                                        |
| Extra memory       | Extra memory for pointers + pointer allocation overhead    | Extra memory for empty slots                              |
| Delete             | Easy: remove from list                                     | Hard: must mark deleted                                   |
| Resizing           | Rebuild bucket array; nodes pointer remain                 | Rebuild entire table; move nodes                          |
| Pointer stability  | Stable: pointers to nodes remain valid                     | Unstable: moving nodes invalidates pointers               |
| Weaknesses         | pointer chasing + allocation/cache overhead                | Poor performance at high load factor + clustering         |
| Best when          | Need flexible load factor / stable objects / easy deletion | Need cache locality, low overhead, high lookup throughput |

### Probing 

| Scheme                     | Probe / rule                                                 | Main advantage                                                         | Main weakness                                                                | Deletion                        |
| -------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------- |
| **Linear probing**         | \(h(k)+i\)                                                   | Very simple, excellent cache locality                                  | **Primary clustering**                                                       | Tombstone or backward shift     |
| **Quadratic probing**      | \(h(k)+c_1i+c_2i^2\)                                         | Avoids primary clustering                                              | **Secondary clustering**; may not visit all slots without careful parameters | Usually tombstone               |
| **Double hashing**         | \(h_1(k)+i\,h_2(k)\)                                         | Good probe distribution; largely avoids primary + secondary clustering | Extra hash computation, worse locality                                       | Usually tombstone               |
| **Python perturb probing** | Recurrence using additional hash bits                        | Different colliding keys tend to get different probe paths             | More complex than basic probing                                              | Tombstones + periodic rebuild   |
| **Robin Hood hashing**     | Usually linear probing + swap if incoming DIB > resident DIB | Reduces variance / long probe lengths; predictable lookup              | Insert/delete may move multiple entries                                      | Usually backward-shift deletion |

Robin Hood use DIB (distance to initial bucket) to determine whether to swap with resident entry. If incoming DIB > resident DIB, swap and continue probing. This reduces variance in probe lengths and makes lookup times more predictable.

The invariant is $D[i + 1] \leq D[i] + 1$ (where $D[i]$ is the DIB of the entry at index $i$).

So for lookup, we can stop when the DIB of current entry is less than the DIB of the key we are looking for.

For deletion, we can use backward shift deletion to maintain the invariant. When we delete an entry, we shift subsequent entries backward until we reach an entry with DIB = 0 or an empty slot.
