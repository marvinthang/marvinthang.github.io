## Process Scheduling (Lecture 3)

A typical process goes through phases of:
* CPU-activity: computation, **Compute-Bound Process** spend majority of its time here
* I/O-activity: waiting for I/O, **I/O-Bound Process** spend majority of its time here

There are 3 categories of Processing Environment:
* Batch Processing: No user interaction required, No need to be responsive
* Interactive (or Multiprogramming): User interaction required, Need to be responsive
* Real-time Processing: have deadline, usually periodic process

Criteria for scheduling are **fairness** and **balance**.

Two types of scheduling policies are **non-preemptive** (cooperative) and **preemptive**.

### Scheduling for Batch Processing

#### Criteria

* Turnaround Time: total time taken (finish time - arrival time), related to waiting time (time spent waiting for CPU)
* Throughput: number of processes completed per unit time
* CPU utilization: percentage of time CPU is busy

#### First-Come-First-Served (FCFS)

Blocked task is removed from the FIFO queue and placed at the back of queue when ready again (just like a new arrival task)

* Guarantee to have no starvation, but can have long waiting time for some processes (convoy effect)

#### Shortest Job First (SJF)

Select task with the smallest next CPU burst time.

* Guarantee smallest average waiting time in simple cases.
* But starvation is possible

To predict CPU Time, we can use **Exponential Average**:

$\tau_{n+1} = \alpha t_n + (1-\alpha)\tau_n$

* $\tau_{n+1}$ = predicted next CPU burst time
* $t_n$ = actual CPU burst time of the current process
* $\tau_n$ = lastest prediction
* $\alpha$ = weight factor (0 < $\alpha$ < 1)

#### Shortest Remaining Time (SRT)

It is SJF but preemptive. If a new process arrives with a smaller CPU burst time than the remaining time of the current process, the current process is preempted.

### Scheduling for Interactive Systems

#### Criteria

* Response Time: time between request and response by systems
* Preditability: less variation in response time, important for real-time systems

Preemptive scheduling is preferred to ensure good response time. Therefore, scheduler needs to run periodically.

If a process never use syscalls, scheduler may never invoke. To avoid this, we can use **timer interrupts** (hardware interrupt) periodically to invoke scheduler.

OS ensure timer interrupt cannot be intercepted by any other program.

#### Terminology

* **Interval of Timer Interrupt** (ITI): OS scheduler is triggered every timer interrupt (constant), usually 1-10ms.
* **Time Quantum**: maximum time a process can run before being preempted (could be constant or variable among the processes, must be multiples of ITI), usually 5-100ms.

#### Round Robin (RR)

Same as FCFS but with time quantum. If a process is not finished after time quantum, it is preempted and placed at the back of the queue.

* Response time guarantee: given n tasks and quantum q, time before a task get CPU is at most (n-1)q.
* Timer interrupt needed: for scheduler to check on quantum expiry.
* The choice of quantum is important:
  * big quantum: better CPU utilization, but worse response time
  * small quantum: better response time, but worse CPU utilization (more time spent on context switching)

> Why not just set ITI = quantum? Because ITI could also be used for other purposes, e.g. updating system clock, checking for I/O completion, etc.
{: .prompt-info }

#### Priority Scheduling

Assign a priority to each process. The scheduler always selects the process with the highest priority to run next.

Variants:
* Preemptive: higher priority process can preempt lower priority process
* Non-preemptive: late arriving higher priority process has to wait for current process to finish

Shortcomings:
* Starvation: low-priority processes may wait indefinitely.

Possible solutions:
* Decrease the priority of a process after it consumes each time quantum.
* Temporarily exclude a process after it consumes its quantum, so it is not considered in the next scheduling decision.

* Hard to guarantee or control the exact amount of CPU time using priority

**Priority Inversion**: a low-priority process holds a resource needed by a high-priority process, causing the high-priority process to wait indefinitely.

#### Multi-level Feedback Queue (MLFQ)

MLFQ learns the process behavior automatically and help minimize both Response Time (for IO bound processes) and Turnaround Time (for CPU bound processes).

MLFQ uses multiple priority queues. New processes start at the highest priority. If a process uses its entire time quantum, it is moved down one priority level; if it gives up the CPU or blocks before the quantum expires, it keeps its current priority.

Shortcomings:
* Starvation: low-priority processes may wait indefinitely.
* Gaming the system: a process may try to manipulate its behavior to get a higher priority.

Fixes: priority boosting, aging, etc.

#### Lottery Scheduling

Give each process a number of lottery tickets. When scheduling, randomly select a ticket and the process holding that ticket gets to run.

In the long run, a process holding X% of tickets uses X% of CPU time.

Properties:
* Responsive: new processes can participate in the lottery immediately
* Good control:
  * Parent process can distribute tickets to child processes
  * Important processes can be given more tickets
  * Each resource (CPU, I/O device, etc.) can have its own lottery
* Simple implementation

## Limited Direct Execution (OSTEP Chapter 6)

### Restricted Operations

Provide:
* user mode: restricted access
* kernel mode: unrestricted access to hardware resources

Special instructions to **trap** into the kernel and **return-from-trap** back to user mode programs are provided, as well as instructions that allow OS to tell hardware where the **trap table** resides in memory.

CPU saves the user execution state needed to resume later (such as the program counter, flags, stack pointer, and other registers) onto a per-thread **kernel stack** before running the trap handler. The kernel stack is trusted kernel-only memory, so it remains valid even if the user stack is invalid or modified, and it is also used for the kernel’s own function calls/local state while handling the trap.

The OS sets up the **trap table** (e.g. x86 IDT) at boot, mapping each trap/interrupt type to a trusted kernel handler. It must be configured again after every reboot because the CPU/RAM state is reset, so the hardware no longer knows where those handlers are.

### Switching Between Processes

#### Cooperative Approach: Wait for syscall

The OS regains control only when a process voluntarily transfers control, such as through a syscall or `yield()`, or when the process performs an illegal operation that causes a trap. If none of these happens, the process can keep running indefinitely.

#### Non-Cooperative Approach: The OS takes control

The OS uses a **timer interrupt** to periodically regain control of the CPU, even if the running process never makes a system call or yields. 

At boot, the OS configures the **trap table** with the **timer interrupt handler** and starts the hardware timer; configuring or disabling the timer is a privileged operation, so user processes cannot prevent preemption.

### Context Switch: Two Levels of State Saving

When process **A** is interrupted while running in user mode, the CPU enters the kernel through the trap/interrupt mechanism. On x86, hardware saves the **minimal user trap frame** (e.g. `RIP`, `RFLAGS`, and user `RSP` on a privilege change) onto A’s kernel stack, while the kernel’s entry assembly saves the remaining user GPRs.

If the scheduler decides to switch **A → B**, the OS executes `switch()` to save A’s **kernel context** - mainly its kernel stack pointer and callee-saved registers - into A’s process/thread structure, then restores B’s kernel context and switches to B’s kernel stack. Finally, `return-from-trap` restores B’s saved user registers and execution state from B’s kernel stack and resumes B in user mode.

```text
A user
→ interrupt/trap
→ save A user context → k-stack(A)
→ scheduler chooses B
→ save A kernel context → proc(A)
→ restore B kernel context ← proc(B)
→ switch to k-stack(B)
→ return-from-trap
→ restore B user context
→ B user
```

**Key idea:** trap entry preserves the **user context**, while `switch()` preserves the **kernel context**.

OS might **disable interrupts** during interrupt processing

### Message Passing

The message is stored in kernel space, and every send/receive involves a syscall.

#### Naming Scheme

* Direct Communication: explicitly specify the recipient/sender process
* Indirect Communication: use mailbox/port to send/receive messages (can be shared by multiple processes)

#### Synchronization

* Blocking Primitives (synchronous): sender/receiver is blocked until the other party is ready
* Non-blocking Primitives (asynchronous): sender/receiver is not blocked

#### Pros and Cons

* Pros:
  * Portable: works across different environments, including different machines and distributed systems
  * Easier synchronization: blocking send/receive can implicitly synchronize the sender and receiver

* Cons:
  * Overhead: send/receive usually requires OS intervention, causing syscall/copying/context-switch overhead
  * Harder to use: data must be packaged into messages, often with size and format constraints

### Unix Pipes

Pipe functions as **circular bounded byte buffer** with **implicit synchronization** (writer blocks if buffer is full, reader blocks if buffer is empty).

Normally, a pipe is **unidirectional**. But there are some variants: multiple readers, multiple writers, bidirectional pipes, etc.

## Process Alternative - Threads (Lecture 5)

Thread switch involves: hardware context switch (registers, SP, PC) and kernel stack switch 

Problems: 
* Parallel syscalls
* Process behavior: handle `fork()`, `exit()`, `exec()`, etc differently

### Implementation

* User thread:
  * Pros:
    * Can have multithreaded on any OS
    * Thread operations are fast (library calls, no kernel intervention)
    * More configurable and flexible (e.g. scheduling policy, thread-local storage)
  * Cons:
    * OS is unaware of threads, so it cannot schedule them independently or exploit multiple cores
* Kernel thread: kernel is aware of threads, and can schedule them independently
  * Pros:
    * Kernel can schedule threads, utilize multiple cores, and exploit parallelism
  * Cons:
    * Thread operations are slower (syscalls, kernel intervention)
    * Less flexible and configurable (e.g. scheduling policy, thread-local storage)
* Hybrid thread: user thread can bind to a kernel thread, offer great flexibility

### POSIX Thread (Pthreads)

It is only the API, and the implementation can be user / kernel thread

* pthread_exit() terminates the calling thread immediately.
  * Useful when called inside a helper function and you want to terminate the whole thread instead of returning back through the call stack.
  * Returning from the thread's start routine also terminates the thread.

Pthreads also have:
* Yield: voluntarily give up CPU to allow other threads to run
* Advanced synchronization: mutex, condition variable, semaphore, etc.
* Scheduling policies: FIFO, Round-Robin, etc.
* Binding to kernel threads
* Etc

## Synchronization (Lecture 6)

### Critical Section 

* Mutual Exclusion
* Progress: if no process is in CS, one of the waiting processes should be granted access
* Bounded Wait: no starvation, exists an upperbound of number of times other processes can enter CS before a waiting process is granted access
* Independence: processes outside CS should not block each other

### Assembly-level Implementation

* Test and Set
* Compare and Exchange
* Atomic Swap
* Load Link / Store Conditional
* Fetch and Add (Ticket Lock)

#### Using Queue and `park()` / `unpark()`

* `park()`: put a thread to sleep
* `unpark()`: wake up a thread

```c
typedef struct __lock_t {
    int flag;
    int guard;
    queue_t *q;
} lock_t;
```

Use a simple spinlock `guard` to protect the lock structure. Because it is only used for a short time to check the lock state and enqueue/dequeue threads, so we can use a simple spinlock.

* `flag`: indicates whether the lock is held or not.
* `q`: a queue of threads waiting for the lock.

We have to release the lock before `park()` because `park()` may block the thread, and if we hold the lock while blocking, other threads cannot acquire the lock and we may have deadlock.

But then we can have **Lost Wakeup Race:** the thread may be woken up by `unpark()` before it calls `park()`, and then it will block forever. To avoid this, we can use `setpark()`.

#### Linux futex

Futex is a **fast userspace wait/wake primitive** in Linux.

`futex_wait(&x, expected)`: only sleeps if `*x == expected`, otherwise returns immediately. This avoids the lost wakeup race.

`futex_wake(&x, n)`: wakes up at most `n` threads waiting on `x`.

```c
void mutex_lock(int *mutex) {
    int v;

    // Try to acquire lock by setting bit 31.
    if (atomic_bit_test_set(mutex, 31) == 0)
        return;

    // Register ourselves as an interested waiter.
    atomic_increment(mutex);

    while (1) {
        // Try acquiring again.
        if (atomic_bit_test_set(mutex, 31) == 0) {
            atomic_decrement(mutex);
            return;
        }

        v = *mutex;

        // bit 31 = 0 => mutex currently unlocked.
        // Don't sleep; retry acquiring it.
        if (v >= 0)
            continue;

        // Sleep only if *mutex is still exactly v.
        futex_wait(mutex, v);
    }
}

void mutex_unlock(int *mutex) {
    // Clear bit 31 by adding 0x80000000.
    // If result becomes 0, there are no interested waiters.
    if (atomic_add_zero(mutex, 0x80000000))
        return;

    // Some waiter exists.
    futex_wake(mutex);
}
```

#### Two-phase Locking

First **spin** briefly hoping the lock becomes available soon; if unsuccessful, block/sleep until being woken. 

It combines the low latency of spinning for short waits with the CPU efficiency of blocking for long waits.

#### Semaphore

Implement counting semaphore using binary semaphore and a counter.

```c++
class CountingSemaphore {
    int count;
    std::binary_semaphore mutex{1};
    std::binary_semaphore gate;

public:
    CountingSemaphore(int initial_count) : count(initial_count), gate(initial_count > 0 ? 1 : 0) {}

    void acquire() {
        gate.acquire();

        mutex.acquire();

        --count;
        if (count > 0) {
            gate.release();
        }

        mutex.release();
    }

    void release() {
        mutex.acquire();

        ++count;

        if (count == 1) {
            gate.release();
        }

        mutex.release();
    }
};
```

Or 
```c++
class CountingSemaphore {
    int count;
    std::binary_semaphore mutex{1};
    std::binary_semaphore gate{0};

public:
    CountingSemaphore(int initial_count) : count(initial_count) {}

    void acquire() {
        mutex.acquire();

        --count;
        if (count >= 0) {
            mutex.release();
        } else {
            mutex.release();

            gate.acquire();

            mutex.release();
        }

    }

    void release() {
        mutex.acquire();

        ++count;

        if (count <= 0) {
            gate.release();
            // we need the `gate` to be acquired before we release the `mutex`, otherwise 
            // many threads can release at the same time, causing the `gate` to be released multiple times, which is not correct for binary semaphore.
        } else {
            mutex.release();
        }

    }
};
```

## Memory Management (Lecture 7)

Two type of data: 
* Transient data: parameters, local variables,...

To create memory abstraction:
* Address relocation
* Base + Limit registers

### Memory Partition

* Fixed-size partition: may create **internal fragmentation** (wasted space within allocated memory)
* Dynamic partition: may create **external fragmentation** / **hole** (wasted space between allocated memory)
  * Allocation Algorithms:
    * First Fit: allocate the first hole that is big enough
    * Best Fit: allocate the smallest hole that is big enough
    * Worst Fit: allocate the largest hole
  * Merging holes: when a process is deallocated, check if adjacent holes can be merged into a larger hole
  * Compaction: move the allocated memory around to create a larger hole, but it cannot be invoked too frequently because it is expensive

Buddy System: provide efficient:
* Partition splitting
* Location good match of free partition
* Partition de-allocation and coalescing

## Disjoint Memory Schemes (Lecture 8)

### Paging

* **Physical frame**: a fixed-size block of physical memory
* **Logical page**: a fixed-size block of logical memory (same size as physical frame)
* **Page Table**: a table that maps logical pages to physical frames

Help remove **external fragmentation** and **compaction**. But it may create **internal fragmentation**.

> Modern hardware supports a **multi-level page table**, which can be viewed as a tree of page-table node: splits one large page table into a tree of smaller tables using different bits of the logical page number for different levels. Lower-level tables are created only when needed, saving memory.
{: .prompt-info }

#### Translation Lookaside Buffer (TLB)

When a context switch occurs, the TLB is flushed to avoid using stale page table entries. Therefore, when a process resume running, it will encounter many TLB misses.

> Memory Management Unit (MMU) and TLB are hardware components, not part of the OS. The OS manages page tables and configures/invalidate TLB state when necessary, while the MMU performs address translation and permission checking.
{: .prompt-info }

> Virtual Memory Area (VMA) is OS/kernel metadata describing a contiguous range of virtual addresses with the same properties, such as access rights and private/shared status. A process may have multiple VMAs for code, data, heap, stack, `mmap` regions, etc.
{: .prompt-info }

##### Who handles TLB misses?

* **Hardware-managed TLB:** the hardware performs the page-table walk, so it must know the **page-table root/base register** and the exact page-table format. It then fills the TLB and continues/retries the memory access.
* **Software-managed TLB:** a TLB miss raises an exception and traps into the OS. The OS looks up the translation, inserts it into the TLB, and returns so the **faulting instruction is retried**; therefore, the saved PC must point to the current instruction, not the next one.
  * The TLB-miss handler must avoid causing another TLB miss while running. Its code, and any memory it immediately depends on such as the handler stack, must therefore be accessible without another miss, e.g. via a **wired/reserved TLB entry** or a **directly mapped physical-memory region**.

##### TLB Contents

A typical TLB might have 32, 64, or 128 entries and be fully associative.

The hardware can search TLB entries in parallel to see if there is a match.

The TLB commonly has a **valid bit** to indicate whether the entry has a valid translation or not. Also **protection bits** (access right bits). There also maybe address-space identifier (ASID), a dirty bit, and so forth.

##### Context Switch

Flushing: on software-based system, this is done by an explicit hardware instruction; with a hardware-managed TLB, the flush could be enacted when the page-table base register is changed. In either case, it is simply setting all valid bits to 0.

Another way is to use address-space ID (ASID) (think of ASID as process ID but with fewer bits (8 bits for the ASID instead of 32 bits for PID)). Then OS must set some privileged register to the ASID of current process.

> **TLB coverage:** If a program’s active pages exceed what the TLB can hold, it suffers many TLB misses and slows down.  
> Using **larger pages** increases coverage (`TLB entries × page size`), which is useful for large, randomly accessed workloads such as DBMSs.
{: .prompt-warning }

**TLB + cache bottleneck:** With a **physically indexed cache**, the CPU must first translate the virtual address through the TLB before it can access the cache, putting TLB latency on the critical path. **Virtually indexed caches** can start the cache lookup using virtual-address bits before translation finishes, improving speed, but they introduce aliasing/coherence complications; modern L1 caches often use **VIPT (Virtually Indexed, Physically Tagged)** as a compromise.

#### Protection

* Access Right Bits: readable, writable, executable. For example, code pages may be `r-x`, while data pages may be `rw-`. The VMA stores the intended access rights for a virtual-memory region, while corresponding permission bits are stored in page table entries for direct hardware checking.

* Valid Bit: indicates whether the **logical page** is valid for the process to access

#### Page Sharing

- For shared code pages (e.g. shared libraries)
- Implement Copy-On-Write (COW)

Access Right Bits also help implement COW when a process is forked:

- Parent and child initially map their corresponding virtual pages to the same physical frame. For pages that were originally writable, **both** PTEs are temporarily marked **read-only**. The parent's PTE must also be read-only; otherwise, the parent could modify the shared physical frame directly and the child would observe the change.
- When either process tries to write to such a page, a write-protection page fault occurs.
- The OS handles the fault and checks the process's VMA. If the region is logically writable and private, the fault may be handled as a COW write. The OS then allocates a new physical frame if necessary, copies the page, updates the faulting process's PTE to point to the new frame, and makes it writable.

### Segmentation Scheme

Each segment (code, data, stack, heap) is mapped to a contiguous range of physical memory with a base address and limit.

The segment name is known as **segment ID**.

Logical address is represented as `<segment ID, offset>`.  
Segment table is used to map segment ID to `<base address, limit>`.

**Hardware** supports segmentation by checking the offset against the limit and adding the base address to the offset to produce a physical address.

**Pros**:

- Each segment is a separate logical memory region
  \=> Can have independent size, protection, and sharing policies

**Cons**:

- External fragmentation: each segment requires a contiguous physical memory region, so free memory may become scattered into small holes

**Observation**: Pure segmentation has little/no internal fragmentation because segments can have variable sizes, but it suffers from external fragmentation. Paging eliminates external fragmentation but may introduce internal fragmentation. Combining segmentation with paging keeps the logical benefits of segmentation while using paging to avoid external fragmentation, at the cost of possible page-level internal fragmentation.

### Segmentation with Paging

Logical address is represented as `<segment ID, page number, offset>`.

The segment table maps each segment ID to `<page-table base address, page limit>`.

The segment limit is now expressed as a **page limit** (number of pages in the segment). Therefore, bounds checking is only at page granularity: an access beyond the actual end of the segment but still within its last page may not be caught.

## Virtual Memory Management (Lecture 9)

To distinguish between two pages types: use a (is memory resident?) bit in PTE.

If not, it raises a page fault, and the OS will load the page from disk into memory, update PTE, and resume the process.

### Page Table Structure

#### 2-Level Paging

Similar to split logical memory space into pages

Split one large page table into smaller page tables, tracked by a **page directory**. The logical page number is divided into a **directory index** and a **page-table index**. Only needed lower-level page tables are created, reducing memory overhead.

#### Inverted Page Table

Keep a simple mapping of physical frame to `<pid, page number>`.

Not a popular design.

### Page Replacement Algorithms

**Memory reference strings**: sequence of **logical page numbers** accessed by a process.

Try to reduce total number of page faults.

#### Optimal Page Replacement (OPT)

Replace the page that will not be used for the longest time in the future.

Guarantees minimum number of page faults, but requires knowledge of future memory references.

Use as a base of comparison for other algorithms.

#### FIFO Page Replacement

OS maintain a queue of resident page numbers, no hardware support needed.

**Belady’s Anomaly**: With FIFO page replacement, increasing the number of frames can sometimes increase the number of page faults. This happens because FIFO evicts pages based only on arrival time and does not exploit **temporal locality**.

#### LRU Page Replacement

Make use of **temporal locality**. Need hardware support

> Exact LRU: Every page access must update its recency information. Since normal memory accesses are handled entirely by hardware without entering the OS, exact LRU requires hardware support to record/update page usage.  
> This overhead is why practical systems usually use approximations such as Clock/Second-Chance.
{: .prompt-info }

Approach A:  Use a time counter, incremented every memory reference. Each page has a time-stamp
* Need to search through all pages
* Time-of-use is forever increase (overflow)

Approach B: Use a recency-ordered doubly linked list

#### Second-Chance Page Replacement (CLOCK)

Each PTE has a reference bit.

The OS maintains a **circular list** of resident pages.

If many pages have `R=1`, Second-Chance has little recency information to distinguish among them and behaves more like FIFO.

### Frame Allocation

* Equal allocation: each process gets the same number of frames
* Proportional allocation: each process gets a number of frames proportional to its size

* Local replacement: a process can only replace its own pages
  * Pros: frames allocated to a process remain constant, so performance is stable between multiple runs
  * Cons: If frames allocated is not enough => hinder the progress of a process
* Global replacement: a process can replace any page in memory
  * Pros: Allow self-adjustment between processes
  * Cons: Badly behaved processes can affect others, and performance may vary between runs

Thrashing: a process is spending more time in page faults than in actual execution.

Insufficient frames allocated => thrashing

If global replacement is used, a thrashing process steals page from other process, cause other process to thrashing (cascading thrashing).

If local replacement is used, thrashing can be limited to one process, but it can hold the I/O and degrade the performance of other processes.

Observation: the set of pages referenced by a process is relatively constant in a period of time (due to locality). However, as time passes, the set of pages can change.

Working Set Model: define the working set window $\delta$, and the working set $W(t, \delta)$ is the set of pages referenced by a process in the time interval $(t-\delta, t)$.

Allocate enough frames to hold the working set of a process, and the process will not thrash.

## File System (Lecture 10)

Physical memory is **volatile**. Direct access to storage is **not portable**.

Criteria:
* Self-contained: all information needed to access files is contained in the file system itself
* Persistent: beyond the lifetime of OS and processes
* Efficient: good management of free and used space, minimal overhead for bookkeeping

Properties:
* Access speed: variable disk I/O time
* Usage: non-volatile **explicit** access (Memory Management is **implicit** access when process is running)

### File

A logical unit of information created by process.

It is an **abstract data type** (ADT, meaning the implementation is hidden from the user) that provides a uniform interface to access data stored on a storage device.

Contains: **data** and **metadata** (or **file attributes**).

File metadata includes:
* Name: A human readable reference to the file
* Identifier: A unique ID for the file used internally by FS
* Type: e.g. executable, text file, object file, directory etc
* Size
* Protection: access permissions
* Time, data, and owner information: creation, last modification, owner id, etc
* Table of content: information for FS to determine how to access the file

#### File Type

Common file types:
* regular file: contains user information
  * ASCII files: text file, programming source code, etc; can be read by humans
  * binary files: executable, pdf file, mp3/4, png/jpeg, etc; have a predefined internal structure that can be processed by specific programs (like PDF reader, media player)
* directories: system files for FS structure
* special files: character/block oriented

Windows commonly uses **file extensions** to indicate file type, while Unix systems can inspect **embedded signatures** (magic numbers) in the file contents. Renaming an extension may change how the OS classifies the file, but does not modify its actual contents.

#### File Protection

* Read
* Write
* Execute: load file into memory and run
* Delete
* List: read metadata of a file

Most general scheme: **Access Control List (ACL)**: Each file has a list of users and their permissions

Permission bits - classify users into 3 classes:
  * Owner (u): the user who created the file
  * Group (g): a set of users who need similar access to a file
  * Other (o): all other users

Access Control List:

#### File Metadata

* Change attributes: File access permissions, dates, ownership, etc

#### Access Methods

* Random access: 
  * read ( offset ) : read data at offset
  * seek ( offset ) : move file pointer to offset

Information OS kept for an opened file:

#### File Information in OS

Use 3 levels conceptually:

* **Per-process FD table:** maps each file descriptor (`fd`) to a kernel open-file entry.
* **System-wide open-file table:** stores state for each open instance, e.g. **current offset, access mode/flags, reference count**, and a pointer to the underlying file.
* **Inode/vnode:** represents the actual filesystem object; stores **metadata + information to locate file data**.

fd → open-file entry → inode/vnode → file data

> When `fork()` or `dup()` is called, the child process shares the **same open-file entry** as the parent, so they share the same file offset and access mode.
{: .prompt-warning }

For normal buffered I/O, file data is cached in the **kernel page cache**.

```text
read()
→ check page cache
→ cache hit: copy data to user buffer
→ cache miss: read from disk into page cache, then copy to user buffer
```

So after `read()`, there are typically **two copies in RAM**:
* one in the kernel page cache
* one in the process's user buffer

The cached copy can be reused by future reads, even from other processes reading the same file.

### Directory

* Single-Level: all files are in the same directory
* Tree-Structure: directories can contain files and other directories (sub-directories)
* Directed Acyclic Graph (DAG): allow multiple paths to the same file (hard links)
* General Graph: allow cycles (symbolic links)

#### Hard Link

A hard link is another filename pointing to the **same inode**.

**Reference counts**
* `link count`: number of directory entries pointing to the inode.
  * `ln` → increment
  * `unlink()` / `rm` → decrement
* `open count`: number of active open references to the file.
  * `open()` → increment open/reference count
  * `close()` → decrement

#### Unix Symbolic Link

A symbolic link is a **special file** that stores the **pathname** of another file/directory.

`G → "/path/to/F" → inode of F → data`

* When `G` is accessed, the OS resolves the stored pathname and then accesses `F`.
* Delete `F` → `G` remains but becomes a **dangling/broken symlink**.

**Overhead**: Higher than a hard link because the symlink is a separate file with its own inode and pathname data.

### I/O Scheduling

![Desktop View](/assets/img/posts/cs2106/magnetic-tape.png){: width="972" height="589" }

Try to reduce seek time.

* FCFS: simple but poor performance
* SSF (Shortest Seek First): select the request with the shortest seek time from current head position
* SCAN: move the head in one direction, servicing requests until it reaches the end, then reverse direction
* C-SCAN: move the head in one direction, servicing requests until it reaches the end, then jump to the other end and continue in the same direction

Newer algorithm:
* Deadline: 3 queues for I/O requests:
  * Sorted queue: sorted by disk location
  * Read FIFO: read requests stored chronologically
  * Write FIFO: write requests stored chronologically
  * Why separate reads/writes? Reads often block the process, while buffered writes can return after writing to the page cache and **flush to disk later**. So reads are usually more urgent.
* noop (No Operation): services requests in the order they arrive, ignoring seek time. Good for SSDs where seek time is negligible.
* CFQ (Completely Fair Queuing): each process has a queue of I/O requests, and the scheduler services them in a round-robin with time-slice.
* BFQ (Budget Fair Queuing, Multiqueue): same as CFQ but with budget based on amount of I/O service.

## File System Implementation (Lecture 11)

General **Disk Structure**:
* Can be treated as a 1D array of **logical blocks**
* Logical block: a fixed-size unit of data transfer between disk and memory (e.g. 512B, 4KB, etc)
* Logical block is mapped into **disk sectors**

Disk Organization:
* **Master Boot Record (MBR)** at sector 0: contains partition table
* Partition table: each can contain an independent file system

A file system contains:
* OS Boot-Up information
* Partition details: 
  * Total number of blocks
  * Number and location of free disk blocks
* Directory Structure
* Files Information
* Actual File Data

### File Implementation

#### File Block Allocation

##### Contiguous

Cons:
* External fragmentation
* File size must be known in advance

##### Linked List

Keep a linked list of disk blocks:
* Each disk block contains the next disk block number
* File information stores first and last disk block number.

Cons:
* Slow random access
* Wasted space for pointers
* Less reliable: if a block is lost, the rest of the file is lost

##### Linked List V2.0 (FAT)

Move all block pointers into a single **File Allocation Table (FAT)**:
* FAT is cached in memory for faster random access

Cons:
* FAT keep tracks of all disk blocks in a partition

##### Indexed Allocation

Each file has an **index block** that contains pointers to all its data blocks.

Cons:
* Limited file size
* Index block overhead: for small files, the index block may be larger than the file itself

##### Extent Tree

Each file has a **tree of extents** that contains pointers to all its data blocks.

Each extent is a contiguous range of disk blocks, so it can be represented by a **starting block number** and a **length**.

> File blocks are often allocated in contiguous ranges because filesystems try to preserve spatial locality. Unlike virtual pages, individual file blocks usually do not require separate per-block metadata, and block lookups are much less frequent than address translations. Therefore, an extent tree is more space-efficient, while its slower lookup is acceptable compared with a page table.
{: .prompt-info }

#### Free Space Management

##### Bitmap

Each disk block is represented by a bit in a bitmap

Pros: provide good set of manipulation operations (e.g. find first free block, find next free block, etc)

Cons: need to keep in memory for efficient access

##### Linked List

Pros: easy to locate free blocks, only need to keep the head of the list in memory

Cons: high overhead (can be mitigated by store the free block list in free blocks)

#### Directory Implementation

File should be opened before use, so we don't need to reopen the file every time we access it.

`open()`: locate the file information using pathname + filename, and store it in the **system-wide open-file table**. Often no data access yet.

##### Linear List

Each entry represent a file:
* Store file name and possible other metadata (e.g. inode number, file type, etc)

Can use cache to remember the last few searches, but still O(n) in worst case.

##### Hash Table

Each directory contains a hash table of size N, usually use chained collision resolution (linked list).

Cons: limited size, depends on good hash function

##### File Information

Consists of: filename and other metadata, possibly disk blocks information

Two common approaches:
* Store everything in directory entry: simple but waste space for small files
* Store only filename and inode number in directory entry, and store other metadata in inode

### Case Study: Extended-2 File System (ext2)

Disk space is split into **blocks**:
* correspond to one or more disk sectors
* are grouped into **block groups**

> Block groups partition one filesystem into local allocation regions, mainly to keep inodes/data close together and make allocation metadata manageable.
{: .prompt-info }

Each file/directory is represented by an **inode** (index node):
* file metadata (permissions, creation time, etc)
* data block addresses

![Desktop View](/assets/img/posts/cs2106/ext2.png){: width="972" height="589" }

Superblock:
* describe the whole FS
* includes:
  * total inodes number, inodes per group
  * total disk blocks, disk blocks per group
  * etc
* Stored in a fixed location on disk, and is **replicated** in each block group for reliability.

Group descriptor Table:
* contains a **group descriptor** for each block group:
  * number of free blocks, free inodes, etc
* Stored in a fixed location on disk, and is **replicated** in each block group for reliability.

Block bitmap: keep track of usage status of each block in the group (1 bit per block)

inode bitmap: keep track of usage status of each inode in the group (1 bit per inode)

inode table: array of inodes, each inode contains metadata and pointers to data blocks

> Why not store inode free in inode table? Because an unused inode slot may still contain stale data; the bitmap gives a tiny, authoritative 1-bit used/free flag that is fast to scan.

#### Multi-level Data Blocks

Multi-level index:
* Similar as multi-level paging
* I-node has a combination of direct indexing and multi-level index scheme

One inode contains:
* 12 direct block pointers: point directly to data blocks
* 1 single indirect block pointer: point to a block that contains an array of direct block pointers
* 1 double indirect block pointer: point to a block that contains an array of single indirect block pointers
* 1 triple indirect block pointer: point to a block that contains an array of double indirect block pointers

#### Directory Structure

Its data blocks contain a sequence of variable length **directory entries**:
* inode number
* size of this directory entry
* length of file/subdir name
* type: file or subdir, etc
* file/subdir name

Removed directory entries are marked with `inode = 0` and can be reused for new entries.

#### Common tasks

To delete a file:
* Remove the directory entry
  * Point the previous entry to the next entry / end
  * to remove first entry: need a blank entry
* update inode bitmap
* update block bitmap

Hard link: Create a directory entry in which use the same inode number as the original file. Increment the link count in the inode.

Symbolic link: create a new file contains pathname of the original file. The new file has its own inode and data blocks.

#### Defragmentation

File fragmentation occurs when a file is stored in non-contiguous blocks on disk, which can lead to increased seek times and reduced performance.

In Linux:
* File allocation algorithm is intelligent:
  * Files are allocated further apart, so that they can grow without running out of space

Keep addition information to recover from system crash.

1. Write the information and / or actual data into a log file
2. Perform the actual operation
